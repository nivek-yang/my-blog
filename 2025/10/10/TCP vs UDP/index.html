TCP vs. UDP：網路世界的快遞員與明信片

發表於 2025-10-10 分類於 技術筆記

當瀏覽網頁、觀看串流影片時，設備正在與遠端的伺服器進行著海量的數據交換。這些數據的傳輸並非隨意進行，而是遵循著一套嚴格的規則，也就是協議 (Protocol)。在傳輸層 (Transport Layer)，有兩位主角幾乎主宰了整個網路世界：TCP 和 UDP。

它們就像郵政系統中的兩種不同服務：一種是提供全程追蹤、簽收保證的快遞服務，另一種則是投進郵筒、隨緣送達的平信明信片。理解它們的差異，是構建任何網路應用的基石。

TCP (Transmission Control Protocol)：可靠的快遞員

想像一下，要寄一份極其重要的合約文件。會選擇一家可靠的快遞公司。整個流程會是這樣的：

  1. 打電話確認 (建立連線): 先打電話給收件人，確保他在家，並且準備好接收文件。這就是 TCP 的 「三次交握」(Three-Way Handshake)。發送方 (SYN) -> 接收方 (SYN-ACK) -> 發送方 (ACK)，雙方建立了一個穩定可靠的連線通道。
  2. 包裹編號 (有序傳輸): 如果合約有好幾頁，會標上頁碼 (1/5, 2/5…)，確保對方能按正確順序閱讀。TCP 會為每個數據包 (Packet) 加上序號，保證接收方能按序重組數據。
  3. 要求簽收 (確認與重傳): 快遞員會要求收件人簽收 (ACK)。如果沒有收到簽收回條，會重新寄送一份。TCP 也有同樣的機制，如果發送方沒有收到對某個數據包的確認，它會重新發送，直到確認收到為止。
  4. 控制流量 (流量控制): 如果一次寄送太多包裹，快遞員的車子裝不下，他會請你慢一點。TCP 的流量控制 (Flow Control) 和擁塞控制 (Congestion Control) 機制確保不會因為發送過快而壓垮接收方或網路。

TCP 的核心承諾：穩定、可靠，數據不多不少、不亂序。

何時使用 TCP？
當數據的完整性和順序性至關重要，不容許任何差錯時：

  • 網頁瀏覽 (HTTP/HTTPS): 不希望網頁的 HTML 標籤或圖片數據丟失一塊吧？
  • 檔案傳輸 (FTP): 下載的檔案絕不能損壞。
  • 電子郵件 (SMTP, IMAP): 郵件內容必須完整無缺。

UDP (User Datagram Protocol)：快速的明信片

想像一下只是想快速地給朋友寄一張風景明信片，分享當下的喜悅。會怎麼做？

寫上地址、貼上郵票，然後直接丟進郵筒。不會打電話確認，也不會要求對方簽收。追求的是簡單、快速。

這就是 UDP 的工作哲學：

  1. 直接寄送 (無連線): 沒有三次交握。數據被打包成「數據報 (Datagram)」後，直接往目標地址扔出去。
  2. 盡力而為 (不可靠): 郵局會盡力寄送，但明信片可能會在途中遺失，也可能因為地址不清而無法送達。UDP 同樣是**「盡力而為」(Best-Effort)**，它不保證數據一定會到達。
  3. 順序隨緣 (無序傳輸): 如果連續寄了 10 張明信片，它們到達的順序可能是隨機的。UDP 不保證數據包的到達順序。
  4. 輕裝上陣 (低延遲): 因為省去了所有確認、重傳、排序的複雜機制，UDP 的數據包標頭 (Header) 非常小，開銷極低，傳輸速度非常快。

UDP 的核心價值：速度至上，延遲極低，但不提供任何保證。

何時使用 UDP？
當速度和即時性遠比偶爾的數據丟失更重要時：

  • 線上遊戲: 玩家的位置、動作需要被即時傳送。延遲一秒遠比丟失某一幀的位置更新更致命。
  • 影音串流/直播 (Streaming): 觀看直播時，寧可畫面偶爾出現一點馬賽克（丟失了一些數據包），也不希望整個畫面為了等待一個遺失的數據包而卡住不動。
  • 語音通話 (VoIP): 同樣，通話的流暢性比單詞的絕對完整更重要。
  • DNS 查詢: 一次快速的域名解析請求，如果失敗了，客戶端可以簡單地再問一次，比建立一個完整的 TCP 連線要快得多。

TCP vs. UDP

特性 TCP (Transmission Control Protocol) UDP (User Datagram Protocol)
比喻 可靠的快遞員 快速的明信片
連線 連線導向 (Connection-Oriented) 無連線 (Connectionless)
可靠性 高，保證送達 低，盡力而為
順序性 有序 無序
速度 較慢 非常快
開銷 (Overhead) 較高 非常低
使用場景 網頁、檔案傳輸、電子郵件 遊戲、串流、語音通話、DNS

實戰應用：網頁開發中的 TCP 與 UDP

回到熟悉的網頁開發，一個關鍵問題是：該如何，或在何時，真正地「使用」TCP 或 UDP 呢？

答案可能有些意外：在網頁開發中，很少會直接去手動操作 TCP 或 UDP。相反地，是透過選擇使用更高層級的 Web API 或技術，來間接地決定使用哪種傳輸協定。

簡單來說：選擇的「工具」，決定了底層用的是 TCP 還是 UDP。

1. 日常的網頁瀏覽與 API 請求 (隱藏的 TCP)

這是佔據了 99% 網頁開發時間的場景。當在 JavaScript 中使用 fetch API、Axios 或傳統的 XMLHttpRequest 來獲取數據、提交表單時，已經在使用 TCP 了，只是你感覺不到。

  • 技術: HTTP/1.1, HTTP/2
  • 底層協定: TCP
  • 原因: 網頁內容的完整性至關重要。TCP 的可靠性完美地滿足了這個需求。
  • 開發者視角:
    // 當寫下這行程式碼時，瀏覽器就在底層處理了複雜的 TCP 連線
fetch('https://api.example.com/data')
  .then(response => response.json())
  .then(data => console.log(data));

2. 即時雙向通訊 (基於 TCP 的 WebSocket)

當需要建立一個持久性的、伺服器可以主動推送訊息給客戶端的場景時（例如：線上聊天室、股票即時報價），會使用 WebSockets。

  • 技術: WebSocket (ws:// 或 wss://)
  • 底層協定: TCP
  • 原因: 聊天訊息或協作指令這類數據，依然希望它們是可靠且按順序到達的。
  • 開發者視角:
    // 建立一個 WebSocket 物件，底層依然是基於 TCP 的長連線
const socket = new WebSocket('wss://api.example.com/chat');
socket.onmessage = (event) => {
  console.log('收到伺服器訊息:', event.data);
};

3. 影音串流與遊戲 (UDP 的主場 WebRTC)

這是在瀏覽器中唯一一個可以大規模使用 UDP 的地方。當在開發視訊會議、語音通話或即時線上遊戲時，WebRTC 是首選。

  • 技術: WebRTC (Web Real-Time Communication)
  • 底層協定: 主要是 UDP
  • 原因: 在即時影音場景中，低延遲比可靠性更重要。寧願丟失一瞬間的數據（畫面出現一點馬賽克），也要保證通話的流暢性。
  • 開發者視角: WebRTC 的 API 相對複雜，但核心是建立 RTCPeerConnection，其數據通道 (Data Channel) 預設就運行在 UDP 之上以實現高速傳輸。

4. 網路的未來 (建立在 UDP 上的 HTTP/3)

新一代的 HTTP/3 協議，其底層不再是 TCP，而是基於 UDP 的一個全新協定叫做 QUIC。

  • 技術: HTTP/3
  • 底層協定: UDP
  • 原因: 為了徹底解決 TCP 的「隊頭阻塞」問題，QUIC 在 UDP 之上重新實現了可靠傳輸，極大地提升了網頁載入速度和弱網環境下的表現。
  • 開發者視角: 這對網頁開發者幾乎是透明的！無需修改 fetch 程式碼。只要瀏覽器和伺服器都支援，它們會自動協商並使用 QUIC 通訊。

總結表：網頁開發中的選擇

技術 (Technology) 底層協定 主要應用場景 開發者如何間接使用
HTTP/1.1, HTTP/2 TCP 網頁瀏覽、API 請求、檔案下載 使用 fetch, axios 等 API
WebSockets TCP 即時聊天、協作工具、消息推送 實例化 WebSocket 物件
WebRTC 主要是 UDP 視訊會議、語音通話、線上直播 使用 RTCPeerConnection API
HTTP/3 UDP (QUIC) 下一代 Web 瀏覽，提升弱網體驗 透明，由瀏覽器和伺服器自動協商

結論

TCP 和 UDP 並非競爭對手，而是網路工具箱中針對不同需求的兩種工具。

作為網頁開發者，雖然很少直接編寫 TCP/UDP 程式碼，但深刻理解這兩種協議的權衡與取捨——可靠性 vs. 低延遲——至關重要。

  • 選擇 TCP，意味著願意為了數據的絕對可靠性而犧牲一點速度。
  • 選擇 UDP，意味著為了追求極致的速度和低延遲，可以容忍一定程度的數據丟失。
