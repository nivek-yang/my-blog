單一登入 (Single Sign-On, SSO) 詳解

發表於 2025-10-11 分類於 技術筆記

是否曾覺得自己的大腦快被各種密碼塞爆了？一組用於電子郵件，另一組給公司的協作平台，第三組用於專案管理，第四組給雲端硬碟……這簡直是一場數位鑰匙的惡夢，也是一個巨大的安全隱患。

如果只需輸入一次主密碼，就能存取所有需要的工具，那該有多好？這並非幻想，而是單一登入 (Single Sign-On, SSO) 所實現的現實。

這篇文章將揭開 SSO 的神秘面紗。

SSO 之前的世界：每項設施都要單獨買票

想像一個超大型的主題樂園，在這裡，每一項遊樂設施、每一個食品攤、每一家紀念品店，都要求在它自己的售票亭單獨買票。想玩雲霄飛車，得排隊付錢；想買個椒鹽卷餅，得去另一個隊伍再付一次錢；想進鬼屋，又是一次排隊、一張新門票。

這就是沒有 SSO 的網路世界。每個應用程式（Slack、Salesforce、Google Drive 等）都是一項獨立的設施。每一個都強迫你透過輸入使用者名稱和密碼來證明身份。這效率低下、令人沮喪，而且很可能弄丟其中一張「門票」（密碼）。

SSO 的運作原理

想像一個現代化的主題樂園。抵達樂園正門，出示身份證明，一次性付清費用。作為回報，他們會給你一個安全、全通行的手環。

在接下來的一整天，都可以自由暢行，再也不用買新的門票。設施的操作員不需要知道你的信用卡詳細資訊，只需要相信樂園正門給了你一個有效的手環。

這正是 SSO 的運作方式。來定義一下這個比喻中的關鍵角色：

  • 使用者 User: 主題樂園的遊客。
  • 樂園正門 (身份提供者 Identity Provider - IdP): 這是驗證身份的中央權威機構。可以把它想像成 Google、Microsoft (Azure AD)，或是公司的登入入口網站。它們是保管密碼的地方。
  • 遊樂設施 (服務提供者 Service Provider - SP): 這些是想要使用的應用程式，如 Salesforce、Slack 或 Dropbox。它們提供服務，但不會直接處理密碼。
  • 魔法手環 (SSO 權杖 Token): 這是一小段安全的數位資訊（通常是 SAML Assertion 或 JWT），在成功登入後，由 IdP 交給瀏覽器。這是一個加密的憑證，相當於：「已經驗證了這個人。可以信任他。」

SSO 的流程

將這趟樂園之旅轉化為技術流程。這一切通常在幾秒鐘內完成：

  1. 嘗試進入一項設施 (SP)： 瀏覽 slack.com。
  2. 設施將你引導至正門 (IdP)： Slack 發現尚未登入。它不會顯示自己的密碼輸入框，而是將你「重定向」到公司的 SSO 登入頁面（也就是 IdP）。
  3. 證明自己的身份： 在 IdP 的登入頁面，輸入帳號密碼（可能還需要多因子認證碼）。
  4. 獲得了魔法手環 (Token)： IdP 驗證身份後，會生成一個安全的 SSO 權杖，並將它傳回給瀏覽器。
  5. 瀏覽器向設施出示手環： 瀏覽器會自動將這個權杖發送給 Slack。
  6. 設施信任這個手環： Slack 收到權杖後，由於它已被設定為信任公司的 IdP，它會驗證權杖的數位簽章，確認是有效使用者，並授予存取權限。

現在，已經成功登入 Slack，而 Slack 根本不知道你的密碼！更棒的是，當下一個目的地是 dropbox.com 時，Dropbox 可能會發現你已經擁有一個來自 IdP 的有效手環，於是自動就讓你登入了，完全無需任何操作。

SSO 的溝通語言：關鍵協議

IdP 和 SP 之間需要一種通用的、安全的語言來交換權杖資訊。目前最常見的兩種協議是：

  • SAML (Security Assertion Markup Language): 企業級 SSO 的主力，尤其適用於網頁應用程式。它功能強大、安全，使用 XML 格式來傳遞資訊。可以把它想像成一份用於身份驗證的、正式且經過公證的信函。
  • OpenID Connect (OIDC) & OAuth 2.0: 這是現代的標準，尤其適用於手機 App 和 API。嚴格來說，OAuth 2.0 用於授權（允許應用程式存取資源），而 OIDC 是建立在其之上的協定，用於認證（證明你是誰）。它通常使用一種更輕量的權杖格式，稱為 JSON Web Token (JWT)。

為什麼 SSO 能創造三贏局面？

採用 SSO 為所有相關方都帶來了巨大的好處。

角色 帶來的好處
使用者 ✅ 便利性： 登入一次，通行無阻。告別密碼疲勞。
IT 與資安管理員 ✅ 集中化的安全管理： 在單一位置強制執行強密碼策略和多因子認證 (MFA)。
✅ 簡化的帳號管理： 新員工入職？只需建立一個帳號。員工離職？停用一個帳號即可立即撤銷所有存取權限。
✅ 更佳的可見性： 從單一入口追蹤誰在存取哪些資源。
企業 ✅ 提升生產力： 減少因忘記密碼或等待 IT 重設而浪費的時間。
✅ 降低風險： 杜絕密碼重用等危險行為，強化整體安全態勢。

開發者視角：SSO 實戰應用與觀念釐清

作為一名網站開發者，最關心的問題是：

  1. 該如何實作 SSO？
  2. 這跟平時用 JWT 做的登入功能，到底有什麼差別？
  3. 如果網站只有一個，需要自己蓋一個 IdP 嗎？

1. 在開發網站時要如何應用 SSO？

在絕大多數情況下，網站會扮演服務提供者 (Service Provider - SP) 的角色。你的任務不是去「打造」一個 SSO 系統，而是去「整合」一個既有的 SSO 系統。

實作的流程大致如下：

  1. 選擇對應的協議庫 (Library): 絕對不需要從零開始手刻 SAML 或 OIDC 協議。社群中已經有非常成熟的函式庫可以幫助處理掉 90% 的複雜工作。
    • Node.js: passport.js 搭配對應的 SAML (passport-saml) 或 OIDC (passport-openidconnect) 策略。
    • Java: Spring Security 內建了強大的 SAML 和 OAuth 2.0/OIDC 支援。
    • Python/Django: django-allauth 或 python-social-auth 都是很棒的選擇。
  2. 與 IdP 進行「信任交換」設定: 這是最關鍵的一步。需要在應用程式後台，以及 IdP 的管理後台（例如 Google、Okta、Azure AD）進行雙向設定。
    • 在 IdP 後台: 需要註冊你的應用程式，並提供一個重要的資訊：回調 URL (Callback URL / Redirect URI)。這個 URL 告訴 IdP 在使用者成功登入後，要把瀏覽器帶回到網站的哪個地址。IdP 會給一組 Client ID 和 Client Secret。
    • 在應用程式後台: 需要配置 IdP 的資訊，例如它的登入端點 URL、發行者資訊 (Issuer)、以及剛才拿到的 Client ID 和 Secret。
  3. 處理回調 (Handle the Callback): 當使用者從 IdP 被引導回來時，回調 URL 會收到一個授權碼 (Authorization Code) 或權杖 (Token)。
    • 後端程式用這個 Code 向 IdP 換取真正的 Access Token 和 ID Token。
    • 選擇的函式庫會自動幫你驗證這個 Token 的簽章是否合法、是否過期。
    • 驗證通過後，從 Token 中解析出使用者資訊（如 Email、姓名）。
    • 核心邏輯: 拿這個 Email 查詢你的資料庫。如果使用者已存在，就幫他建立一個登入狀態（例如 Session）；如果不存在，就為他自動建立一個新帳號，然後再建立登入狀態。

從頭到尾，網站都沒有接觸到使用者的密碼。這就是 SSO 作為 SP 的精髓。

2. SSO 與網站自身的 JWT 認證有何差別？

這是最容易混淆的地方。許多開發者會說：「自己用 JWT 做的登入也是一種 Token-based 認證啊？」是的，但核心區別在於信任的來源。

特性 網站自身的 JWT 認證 SSO (聯邦式認證)
比喻 自己家的鑰匙 公司大樓的門禁卡
誰驗證密碼？ 自己。 後端程式負責驗證使用者提交的帳號密碼是否正確。 外部的 IdP。 完全不管密碼，只相信 IdP 的驗證結果。
誰簽發 Token？ 自己。 驗證密碼成功後，由伺服器簽發一個 JWT 給前端。 外部的 IdP。 IdP 驗證成功後，簽發 Token (SAML/JWT) 並傳遞給你。
誰驗證 Token？ 自己。 前端每次請求都帶著你發的 JWT，後端驗證這個 JWT 是不是自己簽的。 驗證 IdP 的簽章。 收到 IdP 發來的 Token，要驗證這個 Token 確實是由你所信任的那個 IdP 簽發的。
信任範圍 內部 (Internal Trust)。 網站只相信自己發行的 Token。 聯邦式 (Federated Trust)。 網站選擇信任一個外部權威機構發行的 Token。
主要目的 讓使用者在你的單一網站內保持登入狀態。 讓使用者用一組帳密登入多個互相信任的網站。

簡單來說，傳統的 JWT 認證是 「我是法官，我說了算」；而 SSO 整合則是 「我信任隔壁的法官，他蓋了章的文件我都認」。

3. 單一網站需要自己建立一個 IdP 嗎？

通常完全不需要。

建立和維護一個 IdP 是極其龐大且複雜的工程。它的核心價值在於為多個應用程式提供統一的身份驗證服務。如果只有一個網站，那自己就是所有使用者身份的「權威來源」。

在這種情況下，應該選擇的架構是**「網站自身的 JWT 認證」**。由網站自己管理使用者資料庫（包含加密後的密碼）、自己處理登入邏輯、自己簽發和驗證 JWT。這就是絕大多數網站的標準做法。

只有當你是一家大型企業，需要為內部數十個系統（HR、CRM、ERP…）提供統一登入，或者正在開發一個類似 Okta 的商業產品時，才需要考慮建立自己的 IdP。

結論

從本質上，單一登入 (SSO) 的核心在於信任的集中化。不再讓每個應用程式各自為政地負責安全，而是將這項關鍵任務委託給一個單一、強大且高度可信的身份提供者 (IdP)。
