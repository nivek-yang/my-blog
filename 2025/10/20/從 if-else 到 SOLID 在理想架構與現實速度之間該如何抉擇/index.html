從 if-else 到 SOLID：在理想架構與現實速度之間，該如何抉擇？

發表於 2025-10-20 分類於 技術筆記

軟體開發中，需要考慮理想架構與現實速度的權衡。if-else 加上 Feature Flag 的組合，是快速回應需求的利器；而 SOLID 原則，則是追求程式碼長期健康的方案。

這兩者是水火不容的嗎？不。它們其實是功能生命週期的不同階段，一位成熟的工程師，懂得如何在正確的時機使用正確的工具。

The Tactical Choice: if-else + Feature Flag 的戰術價值

首先必須承認，用 if-else 快速增加新功能分支，並不是一種「壞」的實踐，而是一種戰術性選擇。它的核心價值不在於程式碼的優雅，而在於風險控制與快速部署。

優點：

  • 極致的速度：在既有邏輯上增加一個判斷分支，是實現需求最快的方式。
  • 強大的風險控制：新功能有 Bug？關掉 Feature Flag，系統立即恢復舊有行為，無需緊急回滾。
  • 靈活的部署策略：可以輕鬆實現 A/B 測試、灰度發布（Canary Release），將新功能逐步開放給特定用戶群。

缺點：

  • 違反開放封閉原則 (OCP)：直接修改了現有的、本應穩定的程式碼。
  • 累積技術債：每個 if-else 都是一個需要被記住的決策點。當這些分支越積越多，程式碼的複雜度會呈指數級增長，最終變得難以維護。

範例程式碼：

def handle_payment(request):
    # 用一個 flag 快速切換新舊邏輯
    if feature_flags.is_enabled('new-payment-gateway'):
        # 快速實現的新支付邏輯
        return new_payment_service.process(request)
    else:
        # 原有的穩定邏輯
        return old_payment_service.process(request)

結論：Feature Flag 是一種強大的部署工具，而非設計工具。它讓我們能安全地「把鷹架搭在正在行駛的火車上」，但它本身不該成為火車結構的一部分。

The Strategic Goal: SOLID 原則的戰略藍圖

與戰術性的 if-else 相對的，是以 SOLID（特別是開放封閉原則）為代表的戰略性架構。它的目標不是眼前的苟且，而是系統的長期健康與可持續發展。

優點：

  • 結構清晰：職責被清晰地劃分到不同的類別中（符合單一職責）。
  • 易於擴展：未來再增加第三、第四種支付方式時，只需新增對應的策略類別，完全不需碰觸現有穩定程式碼。
  • 可測試性高：每個支付策略都可以被獨立進行單元測試。

缺點：

  • 前期成本較高：為了一個小功能，需要建立介面、建立新類別、修改依賴注入的配置，投入時間較多。
  • 過度設計風險：對於一個不確定是否會長期存在的功能，一開始就投入完整的設計，可能是一種浪費。

範例程式碼 (使用策略模式重構)：

from abc import ABC, abstractmethod

# 1. 定義一個抽象的 "契約"
class PaymentGateway(ABC):
    @abstractmethod
    def process(self, request):
        pass

# 2. 建立具體的 "策略"
class OldPaymentService(PaymentGateway):
    def process(self, request):
        # 原有的穩定邏輯
        print("Processing with old gateway...")

class NewPaymentService(PaymentGateway):
    def process(self, request):
        # 新的支付邏輯
        print("Processing with NEW gateway...")

# 3. 執行程式依賴於 "契約"，而非具體實作
class PaymentHandler:
    def __init__(self, gateway: PaymentGateway):
        self._gateway = gateway

    def handle_payment(self, request):
        # 這裡不再有 if-else
        self._gateway.process(request)

# 在應用程式的配置層或工廠中，決定要注入哪個實例
# 這部分可以根據設定檔或環境變數來決定
if settings.USE_NEW_GATEWAY:
    gateway_instance = NewPaymentService()
else:
    gateway_instance = OldPaymentService()
payment_handler = PaymentHandler(gateway_instance)
payment_handler.handle_payment(some_request)

結論：SOLID 設計是我們追求的最終穩態。它像是一座設計精良的城市，道路寬闊，分區明確，無論未來要蓋新學校還是新醫院，都能輕鬆地找到合適的位置，而不會造成交通堵塞。

實踐之道：一個務實的兩階段工作流

既然兩者各有優劣，該如何結合它們的長處？答案是：將功能開發視為一個從「戰術」到「戰略」的演進過程。

階段一：戰術性部署 (Tactical Deployment)

當接到一個不確定性高或需要快速驗證的需求時：

  1. 擁抱 Feature Flag：大膽地使用 if-else + Feature Flag 的方式，快速將功能交付上線。
  2. 安全驗證：在生產環境中，透過開關 Flag 來驗證功能的正確性與市場反應。
  3. 【最關鍵的一步】建立技術債門票：在專案管理工具（如 Jira, Trello）中，立刻為自己建立一張技術債票，標題為：「重構支付功能的 Feature Flag，將其改為策略模式」。給它設定一個合理的到期日（例如：兩週內）。

階段二：戰略性重構 (Strategic Refactoring)

當新功能被證明是成功的、會長期存在的，就是償還技術債的時候了。

  1. 規劃重構：將技術債門票排入近期的開發週期 (Sprint)。這一步驟必須像開發新功能一樣被正式對待。
  2. 實踐 SOLID：動手移除 if-else，將其重構成前面提到的策略模式。
  3. 清理 Flag：在重構完成並上線穩定後，將無用的 Feature Flag 從程式碼和配置系統中徹底移除。

一個絕佳的比喻是「鷹架」：

Feature Flag 就像蓋大樓時搭的鷹架。它是施工期間保證安全的必要工具，但大樓竣工後，必須把它拆掉。沒有人會住在一個滿是鷹架的房子裡。

SOLID 設計則是大樓穩固的鋼骨結構。

總結

回到最初的問題：實務上該如何選擇？答案是，不必在「單一風格」的死胡同裡打轉，而應該兩者兼顧，並建立一套清晰的團隊紀律。

情境 初期選擇 後續行動
高度不確定的實驗性功能 if-else + Feature Flag 若功能成功，必須排程重構成 SOLID 設計
需要 A/B 測試或灰度發布 if-else + Feature Flag 測試結束後，移除失敗分支並重構保留的分支
確定會長期存在的變化 優先考慮 SOLID 設計 若時間緊迫，可先用 Flag，但要立即建立技術債票
臨時性活動功能 if-else + Feature Flag 活動結束後，必須將整個分支和 Flag 移除

實務上，一個優秀的工程師，既懂得如何利用「鷹架」快速安全地完成工作，也懂得在工作完成後，拆除鷹架，留下一個乾淨、堅固、美觀的建築。兩者兼顧，才是專業的體現。
