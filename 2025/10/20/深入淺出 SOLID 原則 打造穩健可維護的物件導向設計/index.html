深入淺出 SOLID 原則：打造穩健、可維護的物件導向設計

發表於 2025-10-20 分類於 技術筆記

在軟體開發的領域中，我們都追求撰寫出「好」的程式碼。但什麼是「好」的程式碼？除了能夠正確執行外，它還必須具備可讀性、可擴展性、可維護性。隨著專案規模擴大、需求不斷變更，混亂的程式碼結構會成為開發團隊的夢魘。

為了解決這個問題，軟體設計大師 Robert C. Martin (人稱 “Uncle Bob”) 提出了五個物件導向設計的基本原則，也就是著名的 SOLID 原則。遵循這些原則，可以幫助我們建立更穩健、更有彈性、更易於維護的軟體架構。

本篇文章將逐一深入了解 SOLID 的五大原則，並透過簡單的程式碼範例，掌握其核心思想。

Why SOLID? 為何需要這套原則？

在深入每個原則的細節之前，必須先回答一個根本的問題：為什麼需要關心 SOLID？它僅僅是一套學術理論，還是能解決真實世界問題的實用工具？

想像一下，是否遇過以下情境：

  • 脆弱的程式碼：只不過修改了一個看似無關緊要的小地方，卻意外地導致系統其他部分崩潰。
  • 僵化的系統：一個簡單的需求變更，卻需要花費數天甚至數週的時間，在程式碼中進行大規模的修改。
  • 難以重複使用的元件：某個模組的邏輯與系統其他部分緊緊綁在一起，導致無法將它抽出來用在新的專案或功能上。

這些都是「軟體腐敗」(Software Rot) 的典型症狀。SOLID 原則就是對抗這種腐敗的強力武器。它不是一套生硬的規則，而是一套設計哲學，旨在幫助我們從一開始就建立健康的軟體架構。

遵循 SOLID 原則能為帶來以下核心價值：

1. 打造易於維護的程式碼 (Maintainability)

這是最直接的好處。透過單一職責和介面隔離，每個類別的職責都變得清晰且專一。當 bug 出現或需求變更時，能更快地定位到需要修改的程式碼，並且修改所造成的「漣漪效應」也會被控制在最小範圍內。

2. 提升系統的擴展性 (Extensibility)

商業需求總是不斷變化的。開放封閉原則是實現高擴展性的核心。它指導我們設計出這樣的系統：在增加新功能時，只需要新增程式碼，而不是去修改那些已經穩定運行的舊程式碼。這讓系統在成長的過程中依然保持穩定。

3. 降低耦合，提高靈活性 (Decoupling & Flexibility)

依賴反轉原則是實現「解耦」的關鍵。當高階模組（業務邏輯）與低階模組（實作細節，如資料庫、API）分離開來，並同時依賴於抽象介面時，系統就變得極其靈活。可以輕易抽換掉某個元件（例如，將資料庫從 MySQL 換成 PostgreSQL），而不需要改動核心的業務邏輯。

4. 增強程式碼的可讀性與團隊協作 (Readability & Collaboration)

一個遵循 SOLID 原則的專案，其架構是清晰的、可預測的。團隊中的任何人都能更容易地理解每個模組的用途和它們之間的關係，這大大降低了溝通成本，使得團隊協作更加順暢。

5. 讓測試更容易 (Testability)

當類別職責單一且依賴於抽象時，進行單元測試會變得非常簡單。可以輕鬆地為其依賴的抽象介面建立一個「測試替身」(Test Double 或 Mock Object)，從而專注於測試當前類別的邏輯，而不用擔心其依賴項的複雜性。

投入時間學習和實踐 SOLID 原則，是對專案未來的一項重要投資。它能幫助我們避免陷入維護的泥沼，打造出能夠從容應對變化、可持續發展的軟體系統。

什麼是 SOLID？

SOLID 是五個設計原則的縮寫，分別代表：

  • S - 單一職責原則 (Single Responsibility Principle)
  • O - 開放封閉原則 (Open/Closed Principle)
  • L - 里氏替換原則 (Liskov Substitution Principle)
  • I - 介面隔離原則 (Interface Segregation Principle)
  • D - 依賴反轉原則 (Dependency Inversion Principle)
  • 單一職責 (SRP)：讓類別保持專注。
  • 開放封閉 (OCP)：擁抱擴展，避免修改。
  • 里氏替換 (LSP)：確保繼承不會帶來意外。
  • 介面隔離 (ISP)：保持介面的精簡與專一。
  • 依賴反轉 (DIP)：依賴抽象，而非具體實現。

S：單一職責原則 (Single Responsibility Principle, SRP)

核心概念

一個類別 (Class) 應該只有一個引起它變更的原因。

簡單來說，一個類別只應該做好一件事情。如果一個類別承擔了過多的職責，那麼當其中任何一個職責需要變更時，都可能影響到其他的職責，導致類別變得脆弱且難以維護。

為何重要？

  • 降低複雜度：每個類別的職責清晰，更容易被理解。
  • 提高內聚力：相關的功能被集中在同一個類別中。
  • 降低耦合度：職責分離，修改一個職責不會影響到另一個。
  • 易於測試：可以針對單一職責進行單元測試。

程式碼範例

❌ 反面教材：一個類別處理太多事

假設有一個 User 類別，它不僅管理使用者資料，還負責將資料存入資料庫。

class User:
    def __init__(self, name: str, email: str):
        self.name = name
        self.email = email

    def get_user_info(self) -> dict:
        return {"name": self.name, "email": self.email}

    def save_to_database(self):
        # 複雜的資料庫連線與儲存邏輯...
        print(f"Saving {self.name} to the database...")

這個 User 類別違反了 SRP，因為它有兩個變更的理由：

  1. 使用者資料結構的變更 (例如新增年齡屬性)。
  2. 資料庫儲存邏輯的變更 (例如從 MySQL 換成 PostgreSQL)。

✅ 良好實踐：職責分離

應該將職責拆分開來，讓 User 只負責管理使用者資料，並建立一個 UserRepository 專門負責資料庫操作。

class User:
    def __init__(self, name: str, email: str):
        self.name = name
        self.email = email

    def get_user_info(self) -> dict:
        return {"name": self.name, "email": self.email}

class UserRepository:
    def save(self, user: User):
        # 複雜的資料庫連線與儲存邏輯...
        print(f"Saving {user.name} to the database...")

如此一來，當資料庫邏輯需要修改時，只需要改動 UserRepository，完全不會影響到 User 類別。

O：開放封閉原則 (Open/Closed Principle, OCP)

核心概念

軟體實體 (類別、模組、函式) 應該對於擴展是開放的，但對於修改是封閉的。

這意味著當需要為軟體增加新功能時，應該是透過增加新的程式碼來實現，而不是去修改已經存在的程式碼。

為何重要？

  • 穩定性：避免修改現有且穩定的程式碼，減少引入新 Bug 的風險。
  • 擴展性：系統可以輕鬆地增加新功能，而不需要重構核心邏輯。
  • 可維護性：新舊功能彼此獨立，降低維護成本。

程式碼範例

❌ 反面教材：用 if-else 應對新需求

假設有一個 AreaCalculator 用來計算不同形狀的面積。

class Rectangle:
    def __init__(self, width, height):
        self.width = width
        self.height = height

class AreaCalculator:
    def calculate(self, shapes: list) -> float:
        total_area = 0
        for shape in shapes:
            if isinstance(shape, Rectangle):
                total_area += shape.width * shape.height
            # 如果要新增 Circle，就必須修改這裡！
            # if isinstance(shape, Circle):
            #     total_area += shape.radius ** 2 * 3.14
        return total_area

每當需要支援新的形狀 (如 Circle)，就必須回到 AreaCalculator 中增加 if-else 判斷，這就違反了 OCP。

✅ 良好實踐：使用抽象和多型

可以定義一個抽象的 Shape 介面 (或基底類別)，讓所有具體的形狀去實作它。

from abc import ABC, abstractmethod

class Shape(ABC):
    @abstractmethod
    def area(self) -> float:
        pass

class Rectangle(Shape):
    def __init__(self, width, height):
        self.width = width
        self.height = height
  
    def area(self) -> float:
        return self.width * self.height

class Circle(Shape):
    def __init__(self, radius):
        self.radius = radius

    def area(self) -> float:
        return self.radius ** 2 * 3.14159

class AreaCalculator:
    def calculate(self, shapes: list[Shape]) -> float:
        total_area = 0
        for shape in shapes:
            total_area += shape.area() # 不需要知道具體形狀
        return total_area

現在，AreaCalculator 對於修改是封閉的。無論未來增加多少種新形狀 (例如 Triangle)，只要它實作了 Shape 介面，AreaCalculator 的程式碼就完全不需要變動。只需要新增一個 Triangle 類別，這就是對擴展開放。

L：里氏替換原則 (Liskov Substitution Principle, LSP)

核心概念

子類別必須可以替換掉它們的父類別，而不會產生錯誤或破壞程式的行為。

簡單來說，任何使用父類別的地方，都應該能夠透明地使用其子類別的物件，而程式的邏輯不應該因此被破壞。子類別不應該改變父類別預期的行為。

為何重要？

  • 確保繼承的正確性：防止繼承被濫用，確保子類別與父類別行為的一致性。
  • 可預測性：程式的行為不會因為傳入的是子類別物件而產生意外。

程式碼範例

❌ 反面教材：破壞父類別行為的子類別

一個經典的例子是「長方形」和「正方形」。在數學上，正方形是一種特殊的長方形。但在程式設計中，直接繼承可能會出問題。

class Rectangle:
    def __init__(self, width, height):
        self.width = width
        self.height = height

    def set_width(self, width):
        self.width = width

    def set_height(self, height):
        self.height = height

    def get_area(self) -> float:
        return self.width * self.height

class Square(Rectangle):
    def __init__(self, size):
        super().__init__(size, size)

    def set_width(self, width):
        self.width = width
        self.height = width # 正方形的寬高必須相等

    def set_height(self, height):
        self.width = height
        self.height = height

讓我們看看一個使用 Rectangle 的函式：

def test_area(rect: Rectangle):
    rect.set_width(5)
    rect.set_height(4)
    # 我們預期面積是 5 * 4 = 20
    print(f"Expected 20, Got: {rect.get_area()}")

# 使用父類別，行為正常
r = Rectangle(2, 3)
test_area(r) # >> Expected 20, Got: 20

# 使用子類別，行為異常！
s = Square(2)
test_area(s) # >> Expected 20, Got: 16

當 test_area 函式傳入 Square 物件時，set_height(4) 意外地改變了 width，破壞了函式原本的預期行為。這就違反了 LSP。

✅ 良好實踐：使用組合或抽象

解決方案通常是避免不恰當的繼承，可以考慮使用抽象基底類別，讓 Rectangle 和 Square 實作共同的 Shape 介面，而不是讓 Square 繼承 Rectangle。

問題回顧：為什麼繼承是錯的？

Square 繼承 Rectangle 的問題在於，子類 Square 為了維持「寬高必須相等」這個屬於自己的規則，改變了父類 Rectangle 的預期行為（set_width 和 set_height 應該是獨立的）。這就破壞了父類的「契約」(contract)，導致使用父類別的地方無法安全地替換成子類別。

解決方案：從「是一種」(Is-A) 轉向「都屬於」(Is-A-Type-Of)

思維需要轉變：

  • 錯誤的思維：一個正方形「是一種」長方形 (A Square is a Rectangle)。這在數學上對，但在程式行為上是錯的。
  • 正確的思維：一個正方形和一個長方形「都屬於」形狀的一種類型 (A Square and a Rectangle are both types of Shape)。

這個思維轉變引導我們去找出共通的抽象——Shape。

具體實作步驟

步驟 1：定義共通的抽象介面 Shape

使用 Python 的 abc (Abstract Base Classes) 模組來建立一個抽象介面。這個介面的作用是定義一個「契約」：任何自稱是 Shape 的東西，都必須要有一個計算面積 (area) 的方法。

from abc import ABC, abstractmethod

# 定義一個抽象的 Shape 介面
class Shape(ABC):
    """
    這是一個 Shape 的抽象基底類別 (介面)。
    它定義了所有 '形狀' 都應該具備的行為契約。
    """
    @abstractmethod
    def area(self) -> float:
        """
        任何繼承 Shape 的子類別，都必須實作這個 area 方法。
        """
        pass
  • ABC: 表示這是一個抽象基底類別。
  • @abstractmethod: 裝飾器，標明這是一個抽象方法，子類別必須覆寫 (override) 它。
步驟 2：讓 Rectangle 和 Square 都去實作 Shape 介面

讓 Rectangle 和 Square 成為平等的類別，它們不再有繼承關係，而是共同去遵守 Shape 這個契約。

實作 Rectangle 類別：

class Rectangle(Shape):
    def __init__(self, width: float, height: float):
        self.width = width
        self.height = height
  
    # 遵守 Shape 契約，提供 area 方法
    def area(self) -> float:
        return self.width * self.height
      
    def set_width(self, width: float):
        self.width = width
      
    def set_height(self, height: float):
        self.height = height

實作 Square 類別：

class Square(Shape):
    def __init__(self, side_length: float):
        self.side_length = side_length

    # 同樣遵守 Shape 契約，提供自己的 area 實作
    def area(self) -> float:
        return self.side_length ** 2

    def set_side_length(self, side_length: float):
        self.side_length = side_length
  1. Square 不再繼承 Rectangle。它們都直接繼承 Shape。
  2. 它們各自擁有最適合自己的屬性 (width, height vs side_length) 和方法。
  3. 它們都履行了 Shape 的契約，提供了 area() 方法。
步驟 3：修改客戶端程式碼，使其依賴於抽象 Shape

現在，任何需要使用形狀計算面積的函式，不應該依賴於具體的 Rectangle 或 Square，而應該依賴於抽象的 Shape。

# 這個函式依賴於抽象的 Shape，而不是具體的類別
def print_area(shape: Shape):
    """
    這個函式可以接受任何 'Shape' 類型的物件，
    並印出它的面積，它不在乎傳進來的是 Rectangle 還是 Square。
    """
    calculated_area = shape.area()
    print(f"The area of the shape is: {calculated_area}")

# --- 現在來使用它 ---

# 建立一個 Rectangle 物件
rect = Rectangle(5, 4)

# 建立一個 Square 物件
sq = Square(5)

# 將不同類型的物件傳入同一個函式
print("Testing with a Rectangle:")
print_area(rect)  # 輸出: The area of the shape is: 20.0

print("Testing with a Square:")
print_area(sq)    # 輸出: The area of the shape is: 25.0

在這個新的設計中，print_area 函式可以安全地接收任何 Shape 的子類別，因為它只使用了 Shape 契約中保證存在的方法 (area())。它完全不會觸發之前那個因為 set_width 帶來副作用的 bug。

這種做法帶來了顯而易見的好處：

  1. 完全符合 LSP：任何 Shape 的子類別（Rectangle, Square）都可以無縫替換 Shape，而不會產生任何非預期的行為。
  2. 高內聚，低耦合：Square 和 Rectangle 的內部邏輯是獨立的（高內聚）。它們之間沒有了繼承關係，耦合度降到最低，只透過 Shape 介面產生關聯。
  3. 程式碼更清晰穩定：Square 就是 Square，Rectangle 就是 Rectangle。它們的屬性和方法都清晰直觀，符合各自的定義。
  4. 更好的擴展性（符合 OCP）：如果想新增一個 Circle 類別，只需要讓 Circle 也去繼承 Shape 並實作 area 方法，完全不需要修改 print_area 這個函式。

透過這個重構，不僅解決了 LSP 的問題，還讓整個設計變得更加靈活、穩健和可維護。

I：介面隔離原則 (Interface Segregation Principle, ISP)

核心概念

客戶端 (使用介面的類別) 不應該被強迫依賴它們用不到的方法。

與其建立一個龐大、臃腫的「胖介面」(fat interface)，不如將其拆分成多個更小、更具體的介面。

為何重要？

  • 降低耦合：客戶端只需要關心與自己相關的方法。
  • 提高內聚力：每個介面都只服務於一個特定的目的。
  • 靈活性：類別可以根據需要選擇實作哪些小介面。

程式碼範例

❌ 反面教材：一個胖介面

假設有一個 IWorker 介面，定義了工作者的所有行為。

from abc import ABC, abstractmethod

class IWorker(ABC):
    @abstractmethod
    def work(self):
        pass

    @abstractmethod
    def eat(self):
        pass

class HumanWorker(IWorker):
    def work(self):
        print("Human working...")
    def eat(self):
        print("Human eating...")

class RobotWorker(IWorker):
    def work(self):
        print("Robot working...")
  
    def eat(self):
        # 機器人不需要吃東西，但被迫實作這個方法！
        pass

RobotWorker被迫實作一個它根本用不到的 eat 方法，這就是胖介面的問題。

✅ 良好實踐：拆分介面

應該將介面拆分成更小的、職責單一的介面。

class IWorkable(ABC):
    @abstractmethod
    def work(self):
        pass

class IFeedable(ABC):
    @abstractmethod
    def eat(self):
        pass

class HumanWorker(IWorkable, IFeedable):
    def work(self):
        print("Human working...")
    def eat(self):
        print("Human eating...")

class RobotWorker(IWorkable):
    def work(self):
        print("Robot working...")

現在，HumanWorker 同時實作了 IWorkable 和 IFeedable，而 RobotWorker 只需要實作它真正需要的 IWorkable 介面。

D：依賴反轉原則 (Dependency Inversion Principle, DIP)

核心概念

  1. 高階模組不應該依賴於低階模組，兩者都應該依賴於抽象。
  2. 抽象不應該依賴於細節，細節應該依賴於抽象。

簡單來說，就是要「面向介面程式設計」，而不是「面向實作程式設計」。程式碼的依賴關係應該是指向抽象 (介面、抽象類別)，而不是具體的實作類別。

為何重要？

  • 解耦合：高階模組和低階模組之間的耦合度大大降低。
  • 靈活性與可替換性：可以輕易地替換掉低階模組的具體實作，而不影響高階模組。
  • 易於測試：在測試高階模組時，可以輕易地傳入一個「測試用的假物件」(Mock Object)。

程式碼範例

❌ 反面教材：高階模組依賴具體實作

假設有一個 Notification 服務，它需要發送 Email。

class EmailSender:
    def send(self, message: str):
        print(f"Sending email: {message}")

class Notification:
    def __init__(self):
        # 直接依賴具體的 EmailSender
        self.sender = EmailSender()

    def send_notification(self, message: str):
        self.sender.send(message)

這裡，高階模組 Notification 直接依賴了低階模組 EmailSender。如果未來需要增加發送 SMS 或 Push Notification 的功能，就必須修改 Notification 類別，違反了 OCP。

✅ 良好實踐：依賴於抽象

應該定義一個抽象的 IMessageSender 介面，讓高階模組依賴它。

from abc import ABC, abstractmethod

# 1. 定義抽象
class IMessageSender(ABC):
    @abstractmethod
    def send(self, message: str):
        pass

# 2. 低階模組依賴 (實作) 抽象
class EmailSender(IMessageSender):
    def send(self, message: str):
        print(f"Sending email: {message}")

class SmsSender(IMessageSender):
    def send(self, message: str):
        print(f"Sending SMS: {message}")

# 3. 高階模組依賴抽象
class Notification:
    def __init__(self, sender: IMessageSender): # 透過依賴注入
        self.sender = sender

    def send_notification(self, message: str):
        self.sender.send(message)

# 使用方式
email_sender = EmailSender()
notification_email = Notification(email_sender)
notification_email.send_notification("Hello via Email!")

sms_sender = SmsSender()
notification_sms = Notification(sms_sender)
notification_sms.send_notification("Hello via SMS!")

現在，Notification 不再關心是誰在發送訊息，它只依賴於 IMessageSender 這個抽象。可以輕易地注入不同的發送器 (EmailSender, SmsSender) 來改變其行為，而無需修改 Notification 的任何程式碼。這也常被稱為依賴注入 (Dependency Injection)，是實現 DIP 的一種常見模式。

總結

SOLID 原則不是生硬的教條，而是一套經過業界長期實踐、能引導我們寫出更優秀程式碼的設計哲學。

  • 單一職責 (SRP)：讓類別保持專注。
  • 開放封閉 (OCP)：擁抱擴展，避免修改。
  • 里氏替換 (LSP)：確保繼承不會帶來意外。
  • 介面隔離 (ISP)：保持介面的精簡與專一。
  • 依賴反轉 (DIP)：依賴抽象，而非具體實現。

初學者可能覺得要一次遵循所有原則很困難，但不必氣餒。從理解它們背後的思想開始，在下一個專案或下一次重構中，嘗試應用其中一兩個原則。久而久之，將會自然地將這些思想融入程式設計風格中，並體會到它們為專案帶來的巨大好處。

打造一個穩健、可維護的系統，就從實踐 SOLID 開始吧！
