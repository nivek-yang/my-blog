打破數據孤島：深入理解「Data Mesh (數據網格)」

發表於 2025-10-05 分類於 技術筆記

讓我們想像一個在許多成長型企業中反覆上演的劇本：最初，一個集中的數據團隊（Data Team）被建立起來，搭建了數據倉庫（Data Warehouse）或數據湖（Data Lake）。所有的業務數據，從銷售、行銷到營運，都通過複雜的 ETL/ELT 管線匯集於此。起初，一切運作良好。

但隨著業務的擴張，問題開始浮現。數據團隊成了整個組織的瓶頸。業務團隊需要一個新報表？請排隊。數據科學家想接入一個新數據源？需要等待數據工程師的排程。更糟的是，這個集中的團隊雖然擅長技術，卻不完全理解各業務領域數據的細微差別，導致「垃圾進，垃圾出」，數據的可信度大打折扣。

這個集中式的「數據孤島」困境，正是催生下一代數據架構思維——Data Mesh（資料網格）——的根本原因。它不是一個新工具或新平台，而是一個根本性的典範轉移 (Paradigm Shift)，旨在將數據架構從集權的單體（Monolith）模式，推向分散式的網狀生態系統。

什麼是 Data Mesh？

Data Mesh 是一種 現代化的資料管理架構思想，由 Zhamak Dehghani 在 2019 年提出。
它的核心理念是：
👉 讓資料像產品一樣被各領域團隊負責，透過分散式架構來管理和共享，而不是集中在單一資料倉庫 (Data Warehouse) 或資料湖 (Data Lake)。

為什麼需要 Data Mesh？

在深入 Data Mesh 之前，必須理解它要解決的核心問題。傳統 集中式資料平台（例如企業把所有數據丟到一個 Data Warehouse）面臨著幾個難以克服的規模化挑戰：

  1. 組織瓶頸: 資料團隊需要處理所有部門的需求，響應速度慢，無法跟上業務迭代的步伐。
  2. 上下文丟失: 數據的擁有權從最懂數據的業務領域團隊（Domain Team）轉移到了中央數據團隊。後者缺乏業務知識，難以保證數據的品質和業務含義的準確性。
  3. 脆弱的管線: 數百條數據管線交織在一起，錯綜複雜，牽一髮而動全身，維護成本極高。
  4. 責任歸屬模糊: 當數據出錯時，到底是源頭的應用程式團隊的錯，還是數據團隊的錯？責任的推諉屢見不鮮。
  5. 規模問題：當企業規模變大，集中式架構難以擴展。

Data Mesh 透過「分散式」思維解決這些痛點。

Data Mesh 的四大原則

Data Mesh 借鑒了軟體工程領域從「單體應用」走向「微服務」的成功經驗，將同樣的理念應用於數據世界。它的核心思想是：停止將所有數據都拉到一個集中的地方進行處理，而是將數據的所有權和責任歸還給最了解它的業務領域團隊。

為了實現這一點，Data Mesh 建立在四個核心原則之上：

1. 領域導向的分散式數據擁有權 (Domain-Oriented Ownership)

  • 不再由中央資料團隊負責所有數據。

  • 各業務領域（例如：行銷、銷售、物流）自己負責本領域的數據，並對外提供。

  • 例如： 「訂單」相關的分析數據由「電商訂單團隊」擁有和負責；「使用者行為」數據由「使用者增長團隊」擁有和負責。

  • 影響： 這些領域團隊最懂數據的含義、品質標準和業務規則，他們從數據的被動提供者，轉變為主動的擁有者。

2. 數據即產品 (Data as a Product)

這個原則要求我們轉變心態：數據不是技術專案的副產品，而是它本身就是一個產品。 每個領域團隊不僅要擁有自己的數據，還要像對待一個真正的產品一樣，為其「消費者」（公司內的其他團隊）提供服務。

一個好的「數據產品」應該具備以下特質 (D.A.T.A.):

  • 可發現 (Discoverable): 能在統一的數據目錄中輕鬆找到。
  • 可定址 (Addressable): 擁有一個永久、唯一的存取位址（例如 API 端點或表名）。
  • 可信賴 (Trustworthy): 具有明確的服務等級協議（SLA）、數據血緣（Lineage）和品質監控。
  • 可理解 (Understandable) & 自我描述 (Self-Describing): 擁有清晰的 Schema、語義定義和範例數據。

每個領域的數據被視為「產品」，要有清楚的：

  • 文件
  • 品質指標
  • 使用 API 的方式

這樣其他團隊才能放心使用。

3. 自助服務的數據平台 (Self-Serve Data Platform)

要讓領域團隊能夠獨立打造和維護自己的「數據產品」，就不能讓他們從零開始搭建基礎設施。因此，組織需要一個中央的平台團隊（Platform Team）。

這個平台團隊不處理具體的數據內容，而是專注於提供一個自助服務的數據平台。他們提供標準化的工具和服務，涵蓋數據儲存、數據管線、運算、身份認證、數據目錄等，讓領域團隊可以像在雲端平台上使用服務一樣，輕鬆地構建、部署和監控自己的數據產品。

4. 聯邦式計算治理 (Federated Computational Governance)

在一個分散式的世界裡，如何確保數據能夠互通、安全且合規？這就需要一種新的治理模式。

  • 聯邦式 (Federated): 成立一個由各領域數據擁有者、平台團隊和法務/安全代表組成的治理委員會。他們共同制定全域性的規則和標準，例如數據分類標準、隱私政策、安全規範等。
  • 計算 (Computational): 這些規則不應只停留在書面文件上，而應被自動化並植入到自助服務平台中。例如，平台可以自動阻止包含個人身份資訊（PII）的數據被不合規地存取。這就是「治理即程式碼 (Governance as Code)」。

與傳統資料架構比較

特性 傳統 Data Warehouse / Data Lake Data Mesh
架構 集中式 分散式（領域導向）
管理 中央數據團隊 各領域團隊
可擴展性 隨規模成長會遇到瓶頸 更容易水平擴展
資料角色 原始資料，需 ETL 處理 資料即產品，直接可用
治理 中央化 聯邦式

簡單例子

假設一間電商公司：

  • 行銷部門：擁有「廣告點擊數據」
  • 銷售部門：擁有「訂單數據」
  • 物流部門：擁有「配送數據」

在 Data Mesh 下：

  • 每個部門負責自己的資料，並透過標準化 API 提供給其他部門。
  • 例如數據科學團隊要做「廣告 → 訂單轉換率分析」，就能同時取用「廣告數據（行銷部門）」與「訂單數據（銷售部門）」。

常見工具

  • Data Infrastructure: Kafka, Snowflake, Databricks, BigQuery
  • Data Catalog / Governance: Amundsen, DataHub
  • Pipeline: Airflow, dbt

Data Mesh 適合你嗎？

Data Mesh 並非解決所有數據問題的萬靈丹。它更適用於那些已經因規模化而感受到集中式數據平台之痛的大型、複雜的組織。對於小型、業務領域單一的公司，一個傳統的數據倉庫可能仍然是更務實的選擇。

更重要的是，Data Mesh 不僅僅是技術架構的變革，它更是一場深刻的組織和文化變革。它要求企業打破部門牆，賦予領域團隊更大的自主權和責任感。

結論

Data Mesh = 一種 分散式資料架構，透過「領域團隊負責、資料即產品、自助式基礎設施、聯邦治理」四大原則，解決傳統集中式數據平台的擴展與瓶頸問題。

Data Mesh 描繪了一幅數據民主化的藍圖。它通過將責任和能力分散到組織的邊緣，釋放了數據的真正潛力，讓數據真正成為驅動業務創新的燃料，而不是被鎖在中央倉庫裡的負擔。

這條路充滿挑戰，需要技術、組織和文化的協同演進。但對於那些渴望在數據時代保持敏捷和競爭力的企業來說，這無疑是一條值得探索的道路。
