深入底層：資料庫如何在磁碟上儲存資料並透過 SQL 高效查詢？

發表於 2025-10-18 分類於 技術筆記

身為開發者，我們使用 SELECT、INSERT 等 SQL 語法與資料庫互動，但是否曾深入思考：當執行一條查詢時，資料庫的「底層」究竟發生了什麼事？資料表中的數百萬筆紀錄，實際上是以何種形式存在硬碟上？為什麼一個簡單的索引就能讓查詢速度產生天壤之別？

本篇文章將深入資料庫的儲存核心，從磁碟的物理結構開始，逐步揭開資料儲存的神秘面紗，並解析強大的 B-tree/B+ tree 索引是如何幫助 SQL 實現高效的資料操作。

資料實際儲存在哪裡？

當資料儲存在資料庫（如 MySQL 或 PostgreSQL）中時，資料最終是以區塊（Blocks）的形式儲存在磁碟（Disk）上。

磁碟結構與資料單位

  • 磁碟的組成： 磁碟由多個同心圓（邏輯圓圈）組成，這些圓圈稱為磁軌（Tracks）。
  • 區塊/扇區 (Blocks/Sectors)： 磁軌進一步被劃分成扇區（Sectors）。磁軌和扇區的交集部分就是區塊（Blocks）。
  • 資料儲存單位： 資料庫（DBMS）中的資料總是以區塊為單位進行讀取和寫入。一個區塊的大小通常是固定的（例如，出於研究目的，假設為 512 位元組；但在實際資料庫中，例如 PostgreSQL，區塊大小通常為 8K）。
  • 區塊位址： 磁碟上的任何位置都可以透過磁軌號碼和扇區號碼來定位，這就是區塊位址（Block Address）。若要存取區塊中的特定位元組，還需要知道偏移量（Offset）。DBMS 透過這個位址來精準定位資料

從資料表到區塊的映射

資料表 (Table) 在儲存時，會被 DBMS 進行切分，塞進一個個區塊中。

  • 資料表轉換為區塊： 資料表中的每一行（Record/Row）都有特定的位元組大小。
  • 記錄打包： 一個資料表由多筆記錄 (Records/Rows) 組成。DBMS 會計算一條記錄的大小，然後決定一個區塊能容納多少條記錄。如果一條記錄是 128 位元組，那麼一個 512 位元組的區塊就可以儲存 4 條記錄。
  • 分散儲存： 整個資料表會被分割並儲存到多個磁碟區塊中。例如，包含 100 條記錄的表可能需要 25 個區塊來儲存。

主記憶體與磁碟的關係

資料的處理並非直接在磁碟上進行。任何運算都必須遵循「磁碟 -> 記憶體 -> CPU」的流程：

  • 間接存取： 資料不能直接在磁碟上進行處理。
  • 載入 (Load)： DBMS 根據請求，將儲存資料的磁碟區塊讀取到主記憶體 (Main Memory/RAM) 中。
  • 處理 (Process)： 應用程式的程式碼 (例如 SQL 引擎) 在記憶體中對這些資料進行操作。
  • 寫回 (Write-back)： 如果資料被修改，更新後的區塊會被寫回到磁碟上，完成持久化。

DBMS 的核心職責之一，就是設計出一套高效的磁碟資料組織方式，以最小化昂貴的磁碟 I/O 次數。

用 SQL 語法操作資料庫時是怎麼做的？

當使用 SQL 語法（例如 SELECT）查詢資料時，資料庫的目標是最小化磁碟 I/O（Disk Input/Output）操作。這是透過**索引（Indexing）**機制來實現的，特別是透過 B 樹 (B-tree) 和 B+ 樹 (B+ tree) 結構。

索引的必要性與功能

  • 全表掃描的問題： 如果沒有索引，當要查詢一條記錄時，資料庫可能必須執行全表掃描（Full Table Scan），即逐一存取所有儲存該資料表的磁碟區塊。這在大資料量時非常緩慢。
  • 索引的目的： 索引就像一本書的目錄，它是一個獨立於資料的、經過優化的資料結構，可以讓資料庫快速定位所需的資料。
  • 索引的儲存： 索引本身也儲存在磁碟上。索引通常包含一個鍵值（Key）和一個指向資料記錄的指標（Pointer）。

B 樹與 B+ 樹作為索引

B 樹和 B+ 樹是自管理的多級索引（Self-manage Multi-level Indexing），它們是高效能資料庫索引的基礎。

透過索引進行搜尋的流程 (Search Operation)

當執行帶有 WHERE 條件的查詢時，DBMS 的執行流程如下：

  1. 搜尋索引： 資料庫從 B 樹或 B+ 樹的**根節點（Root Node）**開始。
  2. 節點遍歷： 根據查詢的鍵值（Key，例如 1007）與當前節點中的鍵值進行比較，決定要沿著哪個**子指標（Child Pointer）**向下遍歷。
  3. 減少 I/O： 由於 B 樹/B+ 樹具有高分岔度（Degree），意味著一個節點可以有很多子節點。這使得樹的高度非常淺。例如，儲存上億筆記錄的索引樹，其高度可能只有 4-5 層。這也意味著，只需 4-5 次磁碟 I/O，就能從根節點遍歷到包含目標資料指標的葉節點。每往下一個層級，搜索空間就會迅速縮小。樹的高度（即層級數）非常淺，因此只需要存取極少的磁碟區塊就能找到目標。
  4. 取得記錄：
    • B 樹： 鍵值與指向實際資料的指標（Record Pointer）可能儲存在樹的任何節點中。一旦找到鍵值，即獲得記錄指標，然後存取包含該記錄的磁碟區塊。
    • B+ 樹： 鍵值與實際資料（或資料指標）**只儲存在葉節點（Leaf Nodes）**中。找到葉節點後，即可取得資料。

最終，DBMS 只需讀取少數幾個索引區塊和一個資料區塊，就能完成查詢，相較於全表掃描，效能提升是指數級的。

減少 I/O 的實際效益

  • 以 B+ 樹為例： 搜尋過程會讀取索引區塊（非葉節點），然後讀取包含實際資料的區塊。
  • 假設一個表有 25 個資料區塊，如果使用索引，可能只需要讀取 4 個索引區塊和 1 個資料區塊，總共只需存取 5 個區塊，而不是 25 個區塊。這極大地提升了查詢速度。

寫入操作與樹的自平衡 (INSERT / DELETE)

當執行 INSERT 或 DELETE 時，DBMS 不僅要修改資料區塊，還必須同步更新索引樹，並維持其平衡：

  1. 寫入資料區塊： 將實際資料寫入或從磁碟區塊中移除。
  2. 更新索引樹： 根據 B 樹或 B+ 樹的規則，在索引中插入或刪除對應的鍵值。
  3. 維持平衡：
    • 插入 (Insertion)： 若插入導致某個節點的鍵值數量超出上限，該節點會發生分裂 (Splitting)，並將一個中間鍵值上推 (Promoted) 至父節點。此過程可能沿著樹一路向上傳遞，最壞情況下會導致根節點分裂，使樹的高度增加一層。
    • 刪除 (Deletion)： 若刪除導致節點的鍵值數量低於下限 (Underflow)，DBMS 會嘗試從相鄰的兄弟節點借用 (Borrowing) 鍵值，或者與兄弟節點合併 (Merging)。

這些自平衡機制確保了無論資料如何變動，索引樹總能維持極淺的高度，從而保障查詢效能的穩定。

B+ 樹在範圍查詢上的優勢

B+ Tree 相較於 B-Tree 有一個重要的優化：所有的葉節點都透過一個雙向鏈結串列 (Doubly Linked List) 連接在一起，並且是按鍵值順序排序的。

這個特性使得 B+ Tree 在處理範圍查詢 (Range Queries)（例如 WHERE age BETWEEN 20 AND 30）時極為高效：

  1. DBMS 只需透過樹結構找到範圍的起始點 (例如 age = 20)。
  2. 然後，它可以順著葉節點的鏈結串列向後掃描，直到範圍的結束點 (例如 age = 30)，而無需反覆遍歷樹的上層結構。這使得 B+ 樹在處理資料排序和掃描（Sorting and Scanning）方面更有效率。

這就是為什麼 B+ Tree 成為了現代關聯式資料庫索引結構的事實標準。

結論

從磁碟上零散的區塊，到記憶體中待處理的資料，再到 B+ Tree 索引的高效導航，我們可以看到，一個看似簡單的 SQL 查詢背後，是資料庫管理系統數十年來精心設計與優化的結果。理解這些底層原理，不僅能幫助我們寫出更高效能的 SQL，更能讓我們在面對複雜的系統設計與效能瓶頸時，擁有更深刻的洞察力。
