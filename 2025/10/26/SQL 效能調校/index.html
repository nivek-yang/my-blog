SQL 效能調校：當查詢變慢時，該如何找出問題癥結？

發表於 2025-10-26 分類於 技術筆記

“這個查詢在測試環境只要 0.5 秒，為什麼在正式環境要跑 30 秒？”

這句話，可能是每個與資料庫打交道的工程師都曾面臨的惡夢。一個緩慢的 SQL 查詢，輕則影響使用者體驗，重則可能拖垮整個系統。

當問題發生時，不能像無頭蒼蠅一樣亂猜。幸運的是，資料庫本身提供了豐富的線索，我們需要的是一套系統性的偵探方法，從蛛絲馬跡中找出真正的元兇。

這篇文章將提供一個從宏觀到微觀的診斷框架，幫助一步步定位並解決 SQL 效能問題。

第一步：找出有問題的 SQL

先確定「誰」是效能不佳的查詢。

主要工具：慢查詢日誌 (Slow Query Log)

這是生產環境中最直接的線索來源。資料庫可以被設定為自動記錄執行時間超過特定閾值（例如 1 秒）的所有查詢。

  • 如何使用：在資料庫設定檔 (my.cnf for MySQL) 中啟用 slow_query_log，並設定 long_query_time。
  • 可以發現：
    • 哪些查詢經常執行緩慢。
    • 查詢的執行時間、掃描的行數等關鍵指標。
    • 是否有特定使用者或應用程式頻繁發出慢查詢。

重點：定期檢視慢查詢日誌，是主動發現效能隱患的最佳實踐。

第二步：分析執行計畫 (Execution Plan)

找到了慢查詢，下一步就是深入理解資料庫「打算如何執行」這個查詢。這一步是整個效能調校過程的核心。

主要工具：EXPLAIN / Execution Plan

在 SQL 查詢語句前加上 EXPLAIN (MySQL/PostgreSQL) 或檢視 Execution Plan (SQL Server)，資料庫會回傳一份詳細的「執行計畫」，告訴我們它將如何讀取資料、使用索引、以及連接資料表。

EXPLAIN SELECT * FROM orders o
JOIN users u ON o.user_id = u.id
WHERE o.created_at > '2023-01-01';

該關注的關鍵指標：

  1. type (訪問類型)：這是最重要的指標之一。

    • 極差 (ALL)：全資料表掃描 (Full Table Scan)。這是最大的警訊，意味著資料庫需要逐行檢查整張表，沒有使用任何索引。
    • 尚可 (index)：掃描了整個索引，比 ALL 好，但仍有優化空間。
    • 良好 (range, ref, eq_ref)：有效地使用了索引進行範圍查找或精準匹配。
    • 最佳 (const, system)：查詢常數或結果只有一行，速度極快。

  2. key (使用的索引)：顯示資料庫實際決定使用的索引。如果這個欄位是 NULL，而且 type 是 ALL，那幾乎可以確定是索引問題。

  3. rows (掃描的行數)：資料庫預估為了找出結果需要掃描的資料行數。這個數字愈小愈好。如果它遠大於實際返回的行數，代表查詢效率很低。

  4. Extra (額外資訊)：

    • Using filesort：當索引無法滿足排序需求時，資料庫需要將資料拉到記憶體或磁碟中進行額外排序，這會消耗大量資源。
    • Using temporary：資料庫需要建立一個暫存資料表來處理查詢，通常發生在 GROUP BY 或 UNION 操作中，同樣是效能瓶頸。

結論：執行計畫是破案地圖。學會解讀它，就掌握了 SQL 調校的 80% 技巧。

第三步：深入調查 — 常見的效能元兇

根據執行計畫提供的線索，可以開始聚焦在幾個常見的問題點上。

1. 索引問題 (The Usual Suspect)

這是最常見、也最容易解決的問題。

  • 缺少索引：WHERE 條件、JOIN 的關聯欄位 (ON 後面的欄位)、ORDER BY 的欄位沒有建立適當的索引。
  • 索引失效 (Non-SARGable)：在索引欄位上使用函數、進行計算或型別轉換，會導致資料庫無法使用索引。
    -- Bad: 索引失效
WHERE YEAR(order_date) = 2023 

-- Good: 讓索引有效
WHERE order_date >= '2023-01-01' AND order_date < '2024-01-01'
  • 複合索引順序錯誤：對於 WHERE a = 1 AND b = 2 的查詢，INDEX(a, b) 的效率遠高於 INDEX(b, a)。

2. 查詢語句本身的問題

  • SELECT *：請求了不必要的欄位，增加了網路傳輸和資料庫 I/O 的負擔。
  • 不必要的 JOIN：關聯了過多的資料表，或進行了複雜的子查詢。
  • OR 條件過多：有時將 OR 查詢拆成多個 UNION ALL 查詢，效率反而更高。

3. 資料庫狀態問題

  • 統計資訊過時 (Outdated Statistics)：資料庫的查詢優化器依賴統計資訊來制定最佳執行計畫。如果資料表經過大量增刪改後沒有更新統計資訊 (ANALYZE TABLE)，優化器可能會做出錯誤的判斷。
  • 資料庫鎖 (Locking / Deadlock)：查詢可能不慢，但它正在等待其他事務釋放鎖。在高併發的系統中，長時間的交易或不當的鎖定策略會導致查詢阻塞。

4. 系統層面的問題

如果查詢本身和索引都已優化，問題可能出在更底層。

  • 硬體瓶頸：CPU 使用率過高、記憶體不足、或是磁碟 I/O 達到上限。
  • 資料庫設定不當：例如 MySQL 的 innodb_buffer_pool_size 設定過小，導致資料庫頻繁地從磁碟讀取資料，而非記憶體。

總結

步驟 目標 核心工具/方法
1. 發現 從生產環境中找出具體的慢查詢 Slow Query Log、應用效能監控 (APM)
2. 分析 理解資料庫如何執行該查詢 EXPLAIN / Execution Plan
3. 診斷 根據執行計畫，定位根本原因 檢查索引、查詢寫法、鎖定情況
4. 優化 修正問題並驗證效果 建立/修改索引、重寫 SQL、調整設定
5. 監控 持續觀察，防止問題復發 定期檢視日誌，設定警報

SQL 效能調校是一門結合了科學與經驗的藝術。掌握這個系統化的流程，就能自信地應對資料庫效能難題。
