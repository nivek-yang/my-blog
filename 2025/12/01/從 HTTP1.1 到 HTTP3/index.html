從 HTTP/1.1 到 HTTP/3：網路世界的革命，QUIC 協議如何重塑未來？

發表於 2025-12-01 分類於 技術筆記

本篇文章將探索 HTTP/1.1、HTTP/2，以及革命性的 HTTP/3 之間的演進，並揭開其核心驅動力——QUIC 協議的神秘面紗。

HTTP/1.1：穩固的基石與無法忽視的瓶頸

HTTP/1.1 自 1997 年發布以來，一直為我們服務了二十多年。它奠定了現代網路的基礎，但其設計也帶來了幾個難以忽視的性能瓶頸。

核心問題：隊頭阻塞 (Head-of-Line Blocking)

想像一下超市裡只有一個結帳櫃檯。即使只買了一瓶水，如果排在前面的人買了一整車的東西，也只能無奈地等待。

這就是 HTTP/1.1 的工作模式。它在單一的 TCP 連線上，一次只能處理一個請求-回應。瀏覽器為了加快速度，會同時建立多個 TCP 連線（通常是 6 個），但這又帶來了新的資源開銷和 TCP 慢啟動問題。

HTTP/1.1 的主要瓶頸：

  1. 應用層隊頭阻塞： 一個請求被阻塞，後續請求必須等待。
  2. 多個 TCP 連線開銷： 建立和維護多個連線消耗伺服器和客戶端資源。
  3. 無壓縮的標頭 (Header)： 每次請求都帶有大量重複的標頭資訊，浪費頻寬。

HTTP/2：多工處理的重大躍進

為了解決 HTTP/1.1 的問題，HTTP/2 在 2015 年應運而生。它引入了幾個關鍵性的改進，堪稱一次重大升級。

核心改進：多路復用 (Multiplexing)

HTTP/2 最大的亮點是在單一 TCP 連線上實現了多路復用。

想像一下，超市現在升級了，雖然出口還是只有一個，但開了好幾個結帳櫃檯。收銀員可以同時處理好幾個顧客的商品，然後將它們打包（打上標籤），一起送到出口。

這就是 HTTP/2 的運作方式：

  • 二進位分幀 (Binary Framing)： 將 HTTP 訊息分解成更小的、獨立的幀 (Frame)，並以二進位格式傳輸。
  • 串流 (Streams)： 每個請求-回應都被分配一個獨立的串流 ID。這些串流中的幀可以交錯發送，最後在另一端根據 ID 重新組裝。

重要特性：

  • 標頭壓縮 (Header Compression)： 使用 HPACK 算法壓縮標頭，大幅減少了重複數據的傳輸。
  • 伺服器推送 (Server Push)： 伺服器可以在客戶端請求之前，主動將預期資源（如 CSS、JS）推送過去。

新的瓶頸：TCP 層的隊頭阻塞

HTTP/2 完美嗎？不。它雖然解決了應用層的隊頭阻塞，但卻暴露了一個更深層次的問題——TCP 層的隊頭阻塞。

因為所有串流都運行在同一個 TCP 連線上，TCP 協議為了保證數據的順序和可靠性，一旦某個數據包 (Packet) 遺失，它會要求重傳，並暫停後續所有數據包的處理，直到遺失的包被找回。

這就像在多櫃檯結帳的超市，所有打包好的商品都裝在同一輛卡車上運送。如果卡車在路上掉了一個包裹，整輛卡車都必須停下來，直到找回那個包裹，才能繼續前進。這導致車上所有其他人的包裹（即使是完好的）都被延誤了。

這對於網路不穩定（如行動網路）的環境來說，是個致命傷。

HTTP/3 與 QUIC：一次徹底的革新

意識到 TCP 已經成為瓶頸後，業界決定繞過它。HTTP/3 不再基於 TCP，而是選擇了一個全新的傳輸層協議——QUIC (Quick UDP Internet Connections)。

QUIC 最初由 Google 開發，它運行在 UDP 之上。UDP 是一個簡單、無連線的協議，它不保證數據順序或可靠性，像一張白紙，正好讓 QUIC 可以在其上重新實現一套現代化的傳輸機制。

QUIC 如何解決核心問題？

1. 真正解決隊頭阻塞

QUIC 繼承了 HTTP/2 的串流概念，但這些串流是完全獨立的。

繼續我們的比喻：現在超市不再用一輛大卡車送貨，而是為每個顧客的包裹都配備了一架獨立的無人機。一架無人機（一個串流）的延誤或遺失，完全不會影響其他無人機的飛行。

由於 QUIC 基於 UDP，一個串流的數據包遺失，只會影響該串流，協議棧會繼續處理其他串流的數據，從而徹底消除了隊頭阻塞問題。

2. 更快的連線建立 (0-RTT & 1-RTT)

  • TCP 連線： 需要 3 次握手。
  • TCP + TLS 1.2 連線： 總共需要 2-3 個 RTT (Round-Trip Time，來回時延)。
  • QUIC 連線： 將傳輸層和加密層的握手結合在一起。首次連線僅需 1-RTT。對於已經連線過的伺服器，客戶端可以發送加密的「0-RTT」數據，實現零時延的連線建立。

這對於需要頻繁建立短連線的應用來說，性能提升是巨大的。

3. 連線遷移 (Connection Migration)

是否有過這樣的經歷：手機連著 Wi-Fi 看影片，走出家門後網路切換到 4G，影片卡頓了一下甚至需要重新加載？

這是因為 TCP 連線是透過「來源 IP、來源埠、目標 IP、目標埠」這四元組來識別的。網路一換，IP 就變了，連線自然就斷了。

QUIC 使用一個稱為連線 ID (Connection ID) 的獨特標識符來識別連線。無論網路如何切換（IP 地址改變），只要連線 ID 不變，QUIC 就可以無縫地維持連線，不會中斷。

總結

特性 HTTP/1.1 HTTP/2 HTTP/3
底層協議 TCP TCP UDP (QUIC)
多路復用 無 有，單 TCP 連線 有，基於 QUIC 的多個獨立串流
隊頭阻塞 應用層阻塞 TCP 層阻塞 已解決
連線建立 3-RTT (TCP + TLS) 3-RTT (TCP + TLS) 0-RTT 或 1-RTT
標頭壓縮 無 HPACK QPACK (基於 HPACK 改進)
連線遷移 不支援 不支援 支援

結論

從 HTTP/1.1 到 HTTP/3 的演進，是網路協議設計思想的一次根本性變革。它從一個受制於底層 TCP 的應用層協議，演變成一個與傳輸層（QUIC）深度整合、專為現代網路（行動化、不穩定）而生的全新架構。

HTTP/3 和 QUIC 的普及將為我們帶來更快速、更穩定、更安全的網路體驗。下一次當在手機上流暢地切換網路觀看影片時，或許就應該感謝這位幕後英雄——QUIC。
