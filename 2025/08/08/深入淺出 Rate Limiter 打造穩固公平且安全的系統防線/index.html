深入淺出 Rate Limiter：打造穩固、公平且安全的系統防線

發表於 2025-08-08 分類於 技術筆記

想像一下，精心打造的服務上線後大受歡迎，流量一飛沖天。但很快，發現伺服器時常過載、回應緩慢，甚至有用戶抱怨，正常的請求也被惡意程式的刷屏攻擊所淹沒。

這時候，需要一位智慧的「交通警察」來指揮系統的流量，而這位警察的名字，就叫做 Rate Limiter (速率限制器)。

Rate Limiter 不僅僅是一個防禦工具，它更是一種精密的系統設計模式，是現代後端架構中不可或缺的一環。它確保了系統的穩定性、公平性與安全性。

在這篇文章中將探索：

  • 為什麼迫切需要 Rate Limiter？
  • 在哪些真實情境中它能發揮奇效？
  • 如何從零開始，設計一個強大的 Rate Limiter？（包含多種經典演算法）

無論你是後端工程師、系統架構師，或是對建構高可用服務充滿熱情的開發者，這篇文章都將為你帶來紮實的收穫。

為什麼需要 Rate Limiter？不只是為了防禦

很多人對 Rate Limiter 的第一印象是「防止 DDoS 攻擊」，這當然沒錯，但它的價值遠不止於此。一個好的 Rate Limiter 能為系統帶來四大核心好處：

1. 防止惡意攻擊與資源濫用

這是最直接的價值。它可以有效抵禦：

  • 暴力破解 (Brute-force Attack)：限制登入、忘記密碼等 API 的嘗試次數，防止帳號被破解。
  • 憑證填充 (Credential Stuffing)：減緩自動化腳本使用外洩帳密來嘗試登入的攻擊。
  • DDoS 攻擊：透過限制單一來源的請求速率，緩解應用層的 DDoS 攻擊。
  • 資源濫用：防止惡意用戶透過爬蟲或腳本，大量消耗簡訊、郵件或昂貴的第三方 API 額度。

2. 確保系統穩定與服務品質 (QoS)

伺服器、資料庫、快取等後端資源都不是無限的。Rate Limiter 就像一個保險絲，保護下游服務不被突發的流量沖垮，確保整個系統的穩定運行。

3. 維護使用者之間的公平性

如果沒有速率限制，一個「超級用戶」或一個寫得不好的機器人，可能會佔用掉絕大部分系統資源，導致其他所有正常用戶的體驗急遽下降。Rate Limiter 確保每個用戶都能在一個公平的資源配額下使用服務。

4. 滿足商業需求與成本控制

在 SaaS 服務中，Rate Limiter 是實現商業模式的利器。可以為不同的付費方案設定不同的 API 呼叫速率，例如：

  • 免費版用戶：每分鐘 10 次請求
  • 專業版用戶：每分鐘 600 次請求
  • 企業版用戶：無限制或更高的速率

這不僅創造了商業價值，也能有效控制因 API 濫用而產生的運算成本。

Rate Limiter 的典型應用情境

在以下場景中發現 Rate Limiter 的身影：

  • 使用者登入/註冊 API：限制單一 IP 或用戶在短時間內的嘗試次數。
  • 發送簡訊/郵件驗證碼：限制單一手機號碼或信箱在一天內的發送次數，防止「簡訊轟炸」。
  • 對外開放的 Public API：幾乎所有開放平台（如 Twitter, GitHub）都會對 API 進行速率限制。
  • 耗費資源的操作：如圖片上傳處理、報表生成等，限制用戶的發起頻率。
  • 防止網路爬蟲：對爬蟲行為進行限速，保護網站內容與效能。

如何設計一個 Rate Limiter？從演算法到架構

設計 Rate Limiter 的核心問題是：「如何在特定時間窗口內，追蹤並限制一個實體（如用戶 ID、IP 地址）的請求次數？」

讓我們來看看幾種經典的實現演算法，從簡單到複雜，各有千秋。

演算法一：固定視窗計數器 (Fixed Window Counter)

這是最簡單直觀的演算法。

  • 原理：在一個固定的時間視窗內（例如，每分鐘），維護一個計數器。每當有請求進來，計數器就加一。如果計數器超過了閾值，就拒絕請求。當下一個時間視窗開始時，計數器重置為 0。
  • 優點：實現簡單，記憶體消耗小。
  • 缺點：存在邊界問題 (Edge Condition)。如果用戶在時間視窗的邊緣（例如 00:59 和 01:00）發動集中攻擊，他可以在極短時間內發出兩倍於限制的請求，可能導致瞬間流量超標。

演算法二：滑動視窗日誌 (Sliding Window Log)

為了修正固定視窗的邊界問題，這個演算法應運而生。

  • 原理：記錄下每個請求的時間戳。當新請求到來時，計算過去一個時間視窗內（例如，從現在回推 60 秒）有多少個時間戳。如果數量超過閾值，則拒絕請求。
  • 優點：非常精確，完美解決了邊界問題。
  • 缺點：記憶體消耗巨大！因為需要為每個請求儲存時間戳，當流量極大時，這完全不可行。

演算法三：滑動視窗計數器 (Sliding Window Counter)

這是對前兩種演算法的完美平衡，也是業界非常流行的一種方案。

  • 原理：它結合了固定視窗的低記憶體消耗和滑動視窗的平滑性。它將時間視窗切分成更小的格子，並計算當前視窗和前一個視窗的請求數，再根據當前時間在視窗中的比例進行加權計算。
  • 優點：在準確性和資源消耗之間取得了很好的平衡。
  • 缺點：實現比固定視窗複雜一些，但仍比滑動日誌簡單。

演算法四：令牌桶 (Token Bucket)

這是一個非常經典且強大的演算法，能夠應對突發流量 (Bursty Traffic)。

  • 原理：想像一個固定容量的桶，系統會以恆定的速率往桶裡放入「令牌 (Token)」。每個請求都需要從桶裡拿走一個令牌才能被處理。如果桶是空的，那麼請求就會被拒絕或排隊等待。
  • 優點：允許一定程度的突發請求（只要桶裡還有令牌），實現了平滑的速率限制，非常靈活。
  • 缺點：相較於計數器，實現稍微複雜，需要考慮令牌生成和消耗的原子性。

演算法五：漏桶 (Leaky Bucket)

漏桶和令牌桶很像，但目標不同。

  • 原理：請求進來時，先放入一個固定容量的「隊列（桶）」。系統以恆定的速率從隊列中取出請求並處理（就像水從桶底的洞口勻速漏出）。如果隊列已滿，新來的請求將被丟棄。
  • 優點：能強制讓請求以一個平滑、固定的速率被處理，非常適合用來保護下游服務。
  • 缺點：無法應對突發流量，即使系統有空閒資源，請求也必須排隊等待。

演算法比較

演算法 優點 缺點 適用情境
固定視窗計數器 實現簡單，記憶體佔用少 有邊界問題，可能允許瞬間兩倍流量 對精度要求不高的簡單場景
滑動視窗日誌 精確無邊界問題 記憶體消耗巨大 流量不大但對精度要求極高的場景
滑動視窗計數器 精度與性能的良好平衡 實現相對複雜 大多數現代 Web 應用的通用選擇
令牌桶 允許突發流量，靈活性高 實現稍複雜 需要應對突發請求的 API 閘道
漏桶 強制平滑輸出速率 靈活性差，無法應對突發流量 需要保護下游服務，使其穩定接收請求

架構設計上的考量

除了演算法，還有幾個關鍵的架構問題需要思考：

  1. 限制誰？(Granularity)：是針對單一 IP、用戶 ID、API Key，還是某個全局的資源？
  2. 計數器存哪裡？(Storage)：
    • 記憶體：最快，但無法在多台伺服器間共享，且服務重啟後資料會遺失。
    • Redis：業界首選！速度極快、支援多種資料結構（如 HASH、ZSET）、具備原子操作（如 INCR），非常適合在分散式環境中共享狀態。
  3. 分散式環境的挑戰：當服務部署在多台機器上時，必須確保它們共享同一個計數器。這也是 Redis 如此流行的原因。同時，要小心競態條件 (Race Condition)，最好使用 Redis 的 Lua 腳本或原子命令來確保「讀取-修改-寫入」操作的原子性。
  4. 如何回應被拒絕的請求？：一個友好的 Rate Limiter，在拒絕請求時應返回 429 Too Many Requests 狀態碼，並透過 HTTP Header 告知用戶相關資訊，例如：
    • X-RateLimit-Limit: 總請求限制數
    • X-RateLimit-Remaining: 剩餘可用請求數
    • Retry-After: 建議客戶端在多少秒後再試一次

結論

Rate Limiter 絕非一個簡單的「if-else」計數器，它是一門關於平衡、取捨與保護的藝術。它像一道堅固的防線，保護著我們的系統免受惡意攻擊與流量洪峰的衝擊，同時也為用戶提供了公平、穩定的服務體驗。

從簡單的固定視窗到靈活的令牌桶，每種演算法都有其適用的舞台。理解它們的原理與權衡，並結合 Redis 等工具，就能在架構設計上更有信心，打造出企業級的穩固服務。
