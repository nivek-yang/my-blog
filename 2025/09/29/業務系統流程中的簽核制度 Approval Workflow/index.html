業務系統流程中的簽核制度（Approval Workflow）

發表於 2025-09-29 分類於 技術筆記

在企業資訊系統中，簽核制度（Approval Workflow） 是非常常見且關鍵的一環。無論是費用報銷、採購申請、專案立案，還是人事異動，往往都需要經過多層級的審核與批准，確保流程合規、權責明確。

本文將介紹簽核制度的核心概念、常見模式，以及在系統設計上的考量。

為什麼需要簽核制度？

  1. 權責控管
    不同層級的主管對應不同的審批權限，避免越權決策。
  2. 風險管理
    透過層層把關，降低財務或流程上的風險。
  3. 流程透明化
    所有簽核紀錄都能被追蹤，方便稽核與追責。
  4. 自動化效率
    系統化的簽核流程能取代人工傳遞，提高作業效率。

簽核流程的常見模式

1. 單一簽核（Single Approval）

  • 僅需一位主管或負責人批准即可完成。
  • 適用於金額較小或風險較低的流程。

2. 會簽（Parallel Approval）

  • 多位主管需同時審核，全部通過後流程才往下走。
  • 常用於跨部門或跨職能的業務。

3. 逐級簽核（Sequential Approval）

  • 依照組織層級逐層上報，每一層主管批准後才流轉到下一層。
  • 適合金額、風險逐層升高的情境，例如大型採購。

4. 條件式簽核（Conditional Approval）

  • 根據金額、申請類型或部門決定簽核路徑。
  • 例如：金額低於 10 萬由部門主管簽核，高於 10 萬則需總經理批准。

簽核流程範例圖解

以下是一個簡單的「逐級簽核」流程範例：

flowchart TD
    A[申請人提交申請] --> B[部門主管審核]
    B -->|通過| C[財務部審核]
    B -->|退回/駁回| R[結束流程]

    C -->|通過| D[總經理簽核]
    C -->|退回/駁回| R[結束流程]

    D -->|通過| E[完成批准]
    D -->|退回/駁回| R[結束流程]

此流程顯示了：

  • 申請人提交後，需依序經過 部門主管 → 財務部 → 總經理。
  • 任一節點駁回，流程即結束。
  • 全部通過後，申請才正式生效。

系統設計上的考量

在實作簽核制度時，系統需具備以下特點：

  1. 簽核流程定義

    • 可使用資料庫紀錄簽核流程規則（如簽核層級、條件）。
    • 支援配置化，避免硬編碼。

  2. 簽核狀態追蹤

    • 每個簽核節點需有明確狀態（待審、通過、退回、駁回）。
    • 系統需能即時通知下一位簽核人。

  3. 權限控管

    • 確保只有具備對應角色的使用者能簽核。
    • 與使用者角色（Role-Based Access Control, RBAC）整合。

  4. 稽核紀錄

    • 紀錄所有操作時間、使用者、意見，方便追溯。

簽核流程的資料模型範例（以 PostgreSQL 為例）

-- 簽核流程定義
CREATE TABLE approval_flow (
    id SERIAL PRIMARY KEY,
    name VARCHAR(100),
    condition JSONB,         -- 簽核條件（例如金額門檻）
    sequence INT             -- 簽核順序
);

-- 簽核節點
CREATE TABLE approval_step (
    id SERIAL PRIMARY KEY,
    flow_id INT REFERENCES approval_flow(id),
    approver_role VARCHAR(50),
    step_order INT
);

-- 簽核紀錄
CREATE TABLE approval_record (
    id SERIAL PRIMARY KEY,
    step_id INT REFERENCES approval_step(id),
    applicant_id INT,
    approver_id INT,
    status VARCHAR(20),      -- pending, approved, rejected
    comments TEXT,
    created_at TIMESTAMP DEFAULT NOW()
);

這三張表對應到簽核制度的核心元件：

  1. approval_flow

    • 定義一個簽核流程的基本資訊，例如名稱、條件（用 JSONB 記錄金額門檻、部門等規則）、以及流程的順序。
    • 相當於「這是一條簽核路徑」。

  2. approval_step

    • 定義該流程中的每一個簽核節點，例如「部門主管 → 財務 → 總經理」。
    • approver_role 表示這一步需要誰簽核（角色或職位），step_order 控制簽核順序。

  3. approval_record

    • 真正的簽核紀錄，對應到一次具體的「申請」與它的每一個簽核動作。
    • 包含申請人、審核人、狀態（待審、通過、駁回）、意見，以及時間。
    • 相當於「流水帳」或「稽核紀錄」。

👉 這樣的資料設計，可以讓簽核流程 可設定、可追蹤、可擴充。

Django ORM 範例

from django.db import models
from django.contrib.auth.models import User

class ApprovalFlow(models.Model):
    name = models.CharField(max_length=100)
    condition = models.JSONField()
    sequence = models.IntegerField()

class ApprovalStep(models.Model):
    flow = models.ForeignKey(ApprovalFlow, on_delete=models.CASCADE)
    approver_role = models.CharField(max_length=50)
    step_order = models.IntegerField()

class ApprovalRecord(models.Model):
    step = models.ForeignKey(ApprovalStep, on_delete=models.CASCADE)
    applicant = models.ForeignKey(User, related_name="applications", on_delete=models.CASCADE)
    approver = models.ForeignKey(User, related_name="approvals", on_delete=models.CASCADE)
    status = models.CharField(max_length=20, choices=[
        ("pending", "Pending"),
        ("approved", "Approved"),
        ("rejected", "Rejected"),
    ])
    comments = models.TextField(blank=True, null=True)
    created_at = models.DateTimeField(auto_now_add=True)

這段程式碼是把上面的資料表轉換成 Django ORM 的模型：

  1. ApprovalFlow

    • 與 PostgreSQL 的 approval_flow 對應。
    • 存流程名稱、條件、順序。
    • 對應到流程本身，讓系統可以管理不同類型的簽核規則。

  2. ApprovalStep

    • 與 approval_step 對應。
    • 連到某一個流程（flow），定義每個流程的步驟與負責角色。
    • 例如：step 1 = 部門主管，step 2 = 財務，step 3 = 總經理。

  3. ApprovalRecord

    • 與 approval_record 對應。
    • 儲存每次實際申請的簽核狀態。
    • 連到某個簽核步驟（step），記錄申請人、審核人、狀態（approved/rejected/pending）等資訊。
    • 搭配 User 模型，可以知道是誰申請、誰簽核。

有了這些 Django model，就能用 ORM 來存取簽核紀錄，方便進一步實作 API（例如：送出申請、進行簽核、查詢流程狀態）。

實際上在做什麼？

  • 建立流程：先定義一個 ApprovalFlow，加入不同的 ApprovalStep。
  • 送出申請：建立一筆 ApprovalRecord，狀態為 pending。
  • 進行簽核：審核人登入後，修改 ApprovalRecord 的 status 為 approved 或 rejected。
  • 流程推進：若當前步驟通過，系統會自動建立下一步的 ApprovalRecord，直到整個流程完成或中斷。

結論

簽核制度（Approval Workflow）是企業資訊系統中不可或缺的核心機制。
透過 明確的流程設計 與 彈性的系統實作，可以在確保合規與安全的同時，兼顧效率與透明度。

對後端工程師來說，理解簽核制度不僅是資料表設計的問題，更關乎 業務流程的建模能力。
在實務專案中，設計出可擴充、可配置的簽核流程，往往是系統成功的關鍵之一。
