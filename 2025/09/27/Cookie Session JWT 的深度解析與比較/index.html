Cookie, Session, JWT 的深度解析與比較

發表於 2025-09-27 分類於 技術筆記

在瀏覽的網站和使用的應用程式背後，存在一個至關重要的任務：如何安全、有效地管理用戶的狀態與身份？ 無論是登入電商網站後，能繼續購物而無需重複登入；還是呼叫各種 API 服務，系統都能知道是誰、擁有什麼權限，這一切都離不開身份驗證和狀態管理的機制。

長久以來，Cookie 和 Session 一直是網頁應用領域的兩大基石。然而，隨著分散式系統、API 服務和行動應用的興起，一種新的、更具彈性的解決方案逐漸浮現——JWT (JSON Web Token)。這三者各有千秋，但它們的設計理念、工作方式和適用場景卻大相徑庭。

理解它們之間的差異，不僅能幫助在系統設計時做出更明智的選擇，更能在構建安全、高效和可擴展的應用程式時如虎添翼。

Cookie：客戶端的「小紙條」

什麼是 Cookie？

Cookie 是一小段文本信息，由網站的伺服器發送給瀏覽器，然後瀏覽器將其儲存在用戶的本地電腦上。當瀏覽器再次向同一伺服器發送請求時，會將這個 Cookie 攜帶回伺服器。它的主要目的是在無狀態的 HTTP 協議上實現狀態管理。

工作原理

  1. 當訪問一個網站時，伺服器通過 HTTP 響應頭的 Set-Cookie 字段發送一個或多個 Cookie 給瀏覽器。
  2. 瀏覽器接收到 Cookie 後，將其保存在本地。
  3. 之後每一次向該網站發送請求，瀏覽器都會自動將相關的 Cookie 附加在 HTTP 請求頭的 Cookie 字段中發送給伺服器。
  4. 伺服器根據接收到的 Cookie 識別用戶或獲取用戶的狀態信息。

主要屬性

  • Name=Value：Cookie 的名稱和值。
  • Expires / Max-Age：Cookie 的有效期，決定它是會話 Cookie (瀏覽器關閉即失效) 還是持久 Cookie。
  • Domain：指定哪些域名可以讀取這個 Cookie。
  • Path：指定哪些路徑下的請求會發送這個 Cookie。
  • HttpOnly：防止 JavaScript 讀取 Cookie，降低 XSS 攻擊風險。
  • Secure：只在 HTTPS 連接下發送 Cookie。
  • SameSite：防止 CSRF 攻擊 (Strict, Lax, None)。

優點

  • 實現狀態管理：克服 HTTP 無狀態的限制。
  • 數據持久化：可以將數據持久化在客戶端，即使瀏覽器關閉也能保留 (持久 Cookie)。
  • 易於實現：瀏覽器和伺服器都內建支援。

缺點

  • 安全性較差：容易受到 XSS (跨站腳本攻擊) 和 CSRF (跨站請求偽造) 攻擊，特別是沒有設置 HttpOnly 和 SameSite 的 Cookie。
  • 容量限制：每個 Cookie 有大小限制 (通常 4KB)，每個域名下的 Cookie 數量也有限制。
  • 性能開銷：每次 HTTP 請求都會攜帶 Cookie，增加請求頭大小，影響性能。
  • 私隱問題：常用於追蹤用戶行為。
  • 跨域限制：受同源策略限制，難以跨域共享。

適用場景

  • 記住用戶登入狀態 (與 Session ID 配合)。
  • 購物車信息。
  • 用戶偏好設置、主題。
  • 網站分析和追蹤用戶行為。

Session：伺服器端的「會客紀錄」

什麼是 Session？

Session 是一種伺服器端的機制，用於儲存用戶在某個網站上整個會話期間的狀態信息。由於 HTTP 是無狀態的，Session 提供了一種方式，讓伺服器能夠「記住」用戶從一個請求到另一個請求的上下文。

工作原理

  1. 當用戶首次訪問應用程式時，伺服器會創建一個唯一的 Session Id (會話 ID)。
  2. 這個 Session Id 通常會通過 Cookie (稱為 Session Cookie) 發送給客戶端，或者通過 URL 重寫的方式。
  3. 客戶端每次發送請求時，都會將這個 Session Id 帶回伺服器。
  4. 伺服器根據 Session Id 去查找對應的 Session 數據（通常儲存在記憶體、資料庫或快取中），從而識別用戶及其狀態。

主要特點

  • 數據儲存在伺服器端：這意味著敏感數據不會暴露在客戶端。
  • 依賴 Cookie：大多數情況下，Session Id 是透過 Cookie 傳遞的。
  • 有限生命週期：Session 可以設定過期時間，也可以在瀏覽器關閉後失效。

優點

  • 安全性高：所有用戶的敏感數據都儲存在伺服器端，客戶端只保留一個 Session ID，降低了數據洩露的風險。
  • 容量無限制：只要伺服器儲存空間允許，Session 大小沒有理論限制。
  • 易於管理：伺服器可以更好地控制和管理用戶狀態。

缺點

  • 伺服器資源消耗：每個活躍的用戶 Session 都會佔用伺服器資源（記憶體、CPU），在高併發下可能會成為瓶頸。
  • 擴展性問題：在分散式系統或負載均衡環境下，Session 共享變得複雜 (需要引入 Session 共享機制，如 Redis、資料庫集中儲存 Session)。
  • 跨域困難：Session 天然綁定到特定伺服器和域名，跨域或多系統之間共享狀態比較困難。

適用場景

  • 傳統的 Web 應用程式 (如使用 JSP, ASP.NET, PHP 等技術棧)。
  • 需要儲存大量或敏感用戶狀態的場景 (如金融交易)。
  • 用戶登入狀態管理。

JWT (JSON Web Token)：輕量級的「數位簽名令牌」

什麼是 JWT？

JWT (JSON Web Token) 是一個開放標準 (RFC 7519)，它定義了一種緊湊、自包含的方式，用於在各方之間安全地傳輸資訊作為 JSON 物件。這些資訊是數位簽名過的，因此可以被驗證和信任。

JWT 通常用於身份驗證和資訊交換。

結構

一個 JWT 包含了三部分，由點 (.) 分隔：Header.Payload.Signature。

  1. Header (頭部)：

    • 通常包含兩個字段：typ (Token 類型，通常為 “JWT”) 和 alg (使用的簽名算法，例如 HMACS SHA256 或 RSA)。
    • 範例：{"alg": "HS256", "typ": "JWT"}
    • 接著會用 Base64URL 編碼。

  2. Payload (載荷)：

    • 包含實際需要傳輸的數據，稱為 claims (聲明)。
    • claims 又分為三種類型：
      • 標準聲明 (Registered Claims)：如 iss (發布者), exp (過期時間), sub (主題), aud (接收者) 等，建議使用但非強制。
      • 公開聲明 (Public Claims)：用戶自定義的聲明，但為避免衝突，建議將其定義為 URI 形式。
      • 私有聲明 (Private Claims)：應用程式之間自定義的聲明，不需要唯一性。
    • 範例：{"sub": "1234567890", "name": "John Doe", "admin": true, "exp": 1678880000}
    • 接著也會用 Base64URL 編碼。

  3. Signature (簽名)：

    • 將編碼後的 Header 和 Payload，以及一個祕密 (secret) 或私鑰，使用 Header 中指定的算法進行簽名。
    • 公式：HMACSHA256(base64UrlEncode(header) + "." + base64UrlEncode(payload), secret)
    • 簽名的目的是驗證 Token 的完整性（確保沒有被篡改）和真實性（證明是由已知簽發者簽發）。

工作原理

  1. 用戶登入時，伺服器驗證其憑證。
  2. 驗證成功後，伺服器生成一個 JWT，其中包含用戶的身份信息和權限。
  3. 伺服器將這個 JWT 返回給客戶端（通常在 HTTP 響應體中或作為 Cookie）。
  4. 客戶端（例如瀏覽器/行動應用）接收到 JWT 後，將其儲存在本地（例如 Local Storage、Session Storage 或 Cookie）。
  5. 之後每一次發送需要驗證的請求時，客戶端將 JWT 附加在 HTTP 請求頭的 Authorization 字段中（通常以 Bearer 方案）。
  6. 伺服器接收到請求後，會使用相同的祕密或公鑰驗證 JWT 的簽名。
  7. 驗證成功後，解析 Payload 獲取用戶身份和權限，然後處理請求。伺服器不需要儲存任何 Session 狀態。

優點

  • 無狀態 (Stateless)：伺服器無需儲存用戶 Session 狀態，提升了伺服器擴展性 (特別是對於分佈式系統和微服務)。
  • 可擴展性高：由於無狀態，容易在多個伺服器之間共享，非常適合微服務架構和負載均衡。
  • 跨域/跨平台：可以在不同域名或不同應用程式 (Web, Mobile App) 之間傳遞和驗證。
  • 資訊自包含：Token 中包含所有必要信息，減少資料庫查詢。
  • 安全性 (簽名)：Token 經過簽名，防止篡改，保證數據完整性。

缺點

  • Token 無法作廢：一旦簽發，在過期時間之前，無法直接讓其失效（除非伺服器另設黑名單機制）。這對安全性有影響 (例如用戶登出或權限變更時)。
  • Secret 洩漏風險：如果用於簽名的 Secret 洩漏，Token 可能被偽造。
  • Token 容量：如果 Payload 包含過多信息，JWT 會變大，增加網絡傳輸開銷。
  • 安全性 (未加密)：Payload 只是 Base64 編碼，並非加密，任何人都可解碼讀取。因此不適合儲存敏感數據。
  • XSS 風險：如果 JWT 儲存在 Local Storage，容易受到 XSS 攻擊而洩漏。

適用場景

  • API 身份驗證：特別是 RESTful API，不需要傳統 Session 狀態。
  • 微服務架構：服務間進行身份和權限驗證。
  • 單點登入 (SSO)：在多個應用程式之間共享用戶身份。
  • 行動應用：作為身份驗證憑證。

Cookie, Session, JWT 的核心差異對照表

特性 Cookie Session JWT (JSON Web Token)
儲存位置 客戶端 (瀏覽器) 伺服器端 (記憶體、DB、Redis 等) 客戶端 (Local Storage, Session Storage, Cookie)
伺服器狀態 無狀態 (但與 Session 搭配時傳遞 Session ID) 有狀態 (伺服器需維護 Session 數據) 無狀態 (伺服器不儲存 Token 數據，只驗證簽名)
擴展性 差 (受限於同源策略和容量限制) 差 (須額外機制實現 Session 共享) 高 (天然支援分散式和負載均衡)
安全性 容易被 XSS/CSRF 攻擊 (若無適當防護) 高 (敏感數據在伺服器) 簽名防篡改，但數據公開，需防 XSS 洩漏 Token
數據容量 小 (通常 4KB) 大 (理論上無限，受限於伺服器資源) 通常較小 (越大傳輸開銷越大)
傳輸開銷 每次請求都會攜帶，增加請求頭大小。 攜帶 Session ID (通常較小)。 每次請求攜帶整個 Token，Token 越大開銷越大。
作廢機制 可直接設定過期時間或伺服器移除。 伺服器可隨時失效 Session。 需額外黑名單機制，否則過期前無法直接作廢。
主要用途 用戶偏好、狀態追蹤，傳遞 Session ID 用戶登入狀態、購物車、敏感數據儲存 API 身份驗證、單點登入、微服務認證

什麼時候選用誰？

  • 傳統的 Web 應用，且大部分操作圍繞單一伺服器 (單體架構) → Cookie + Session

    • 這種組合在許多傳統 Web 框架中是預設且成熟的方案。
    • 安全性較高，因為敏感數據仍保留在伺服器。
    • 缺點是橫向擴展性差，需要考慮 Session 共享問題。

  • 需要無狀態、高擴展性、跨域/跨平台的 API 認證，特別是微服務、前後端分離、行動應用 → JWT

    • JWT 讓 API 變得真正無狀態，便於擴展和部署。
    • 適用於需要為眾多客戶端（Web, iOS, Android）提供統一認證接口的場景。
    • 但需要注意 Token 的安全儲存 (避免 XSS 攻擊) 和作廢機制。

  • 在有狀態的應用中，需要儲存少量的非敏感信息在客戶端，或用於與 Session 搭配傳遞 Session ID → 純 Cookie

    • 例如記錄用戶的語言偏好、夜間模式設置等。
    • HttpOnly 和 Secure 屬性必須嚴格設定以增強安全性。

最佳實踐與結合使用

有時候，甚至會將 JWT 和 Cookie 結合起來使用，以發揮各自的優勢並彌補不足：

  • HttpOnly Cookie 儲存 JWT：
    • 將 JWT 儲存在設定了 HttpOnly 和 Secure 屬性的 Cookie 中。
    • HttpOnly 可以防止 XSS 攻擊直接從 JavaScript 讀取 JWT。
    • Secure 可以確保 JWT 只在 HTTPS 連接中傳輸，防止中間人攻擊。
    • 這樣做既利用了 JWT 的無狀態特點，又利用了 Cookie 的安全性優勢 (對抗 XSS)。
    • 但仍可能面臨 CSRF 攻擊，需要搭配 SameSite 屬性或 CSRF Token 來防範。

結論

Cookie、Session 和 JWT 各自在 Web 應用和 API 身份驗證與狀態管理中扮演著不可或缺的角色。它們就像是工具箱中的不同工具，沒有絕對的優劣，只有最適合特定任務的選擇。

理解它們的設計哲學、技術細節和權衡考量，是成為一名優秀的系統設計者和開發者的關鍵一步。
