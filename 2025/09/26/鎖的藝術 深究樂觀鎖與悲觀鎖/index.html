鎖的藝術：深究樂觀鎖與悲觀鎖

發表於 2025-09-26 分類於 技術筆記

在多用戶、高併發的應用程式世界裡，資料的正確性與一致性是時刻需要捍衛的。想像一下，兩位用戶同時嘗試購買最後一件商品，或者系統在處理一筆交易時發生網路延遲，導致同一筆金額被扣款兩次。這些情境若處理不當，輕則造成數據混亂，重則可能導致嚴重的業務損失和客戶信任危機。

這些問題的核心，都指向一個挑戰：如何管理對共享資源的併發存取？

而解決之道，往往需要引入一個強大的機制——鎖 (Lock)。鎖是併發控制的基石，它允許我們在多個操作共享同一份數據時，確保每一次的讀取或寫入都能以一種可預期、可控的方式進行，從而維護數據的完整性。

這篇文章就讓我們一同深入探索資料庫中鎖的奧秘，特別是兩大經典策略：樂觀鎖 (Optimistic Lock) 與 悲觀鎖 (Pessimistic Lock)，理解它們的哲學、工作原理、適用場景及權衡考量，幫助在設計系統時，選擇最合適的「數據守護者」

為什麼需要鎖？

在一個併發環境中（即多個進程或線程同時存取和修改數據），如果沒有適當的控制機制，可能會出現以下典型的數據不一致問題：

  1. 丟失更新 (Lost Update)：兩個事務同時讀取同一條數據，各自修改後寫回，後寫回的會覆蓋先寫回的修改，導致一個事務的修改丟失。
  2. 髒讀 (Dirty Read)：一個事務讀取了另一個事務尚未提交的數據。如果那個未提交的事務最終回滾，那麼讀取到的數據就是「髒」的。
  3. 不可重複讀 (Non-Repeatable Read)：在同一個事務中，兩次讀取同一條數據，由於期間有其他事務修改並提交了該數據，導致兩次讀取到的結果不同。
  4. 幻影讀 (Phantom Read)：在同一個事務中，兩次執行相同的查詢條件，第二次查詢卻發現了第一次查詢中沒有的新增或刪除數據。

鎖的存在，正是為了解決這些問題，確保數據在併發操作下的隔離性 (Isolation) 和一致性 (Consistency)。

悲觀鎖 (Pessimistic Lock)

核心哲學

悲觀鎖的哲學是：「永遠假設最壞的情況會發生」。它認為在併發環境下，數據衝突是常態，因此在讀取或修改數據之前，就先獨佔式地鎖定該數據資源，直到該操作完成並釋放鎖為止。這就像在開始工作前，先用一把大鎖把辦公室鎖起來，確保沒有人會和你搶電腦。

工作原理

在資料庫層面，悲觀鎖通常透過資料庫本身的鎖機制來實現。最常見的，是在 SQL 查詢時使用 SELECT ... FOR UPDATE 或 SELECT ... FOR SHARE 語句：

  • SELECT ... FOR UPDATE (排他鎖/寫鎖)：

    • 當一個事務執行此語句時，會對被選中的行（或整個表，取決於資料庫引擎和隔離級別）施加排他鎖。
    • 在該事務提交或回滾之前，其他任何事務都無法讀取或修改這些被鎖定的行。它們會被阻塞 (Block)，直到鎖被釋放。
    • 範例：銀行轉帳，從 A 帳戶扣款 A’，往 B 帳戶加款 B’。在讀取 A 帳戶餘額時就對 A 帳戶行加排他鎖，防止其他併發交易篡改此餘額。

  • SELECT ... FOR SHARE (共享鎖/讀鎖)：

    • 允許多個事務同時持有同一數據的共享鎖，即多個事務可以同時讀取這些數據。
    • 但是，任何嘗試修改（寫入）這些數據的事務都會被阻塞，直到所有共享鎖都被釋放。
    • 範例：查詢商品庫存，在讀取時施加共享鎖，確保在讀取期間沒有人更改庫存數量。

優點

  • 數據安全性高：保證數據的強一致性，徹底避免丟失更新等問題。
  • 簡單直接：資料庫系統本身處理鎖的獲取和釋放，應用程式層面的邏輯相對簡單。

缺點

  • 併發性低：由於鎖定資源會阻塞其他操作，大大降低了系統的併發處理能力。若鎖定範圍過大或時間過長，會成為系統瓶頸。
  • 死鎖風險 (Deadlock Risk)：當兩個或多個事務互相等待對方釋放鎖時，就會發生死鎖。這需要複雜的機制來檢測和解決。
  • 不適用於分佈式系統：資料庫層面的悲觀鎖是針對單一資料庫實例設計的，很難在多個微服務、多個資料庫實例之間實現有效的悲觀鎖。

適用場景

  • 高寫入衝突：預期會有大量併發寫入操作，且數據一致性要求極高。
  • 事務時間短：鎖定資源的時間非常短暫，能迅速完成事務並釋放鎖。
  • 銀行轉帳、庫存扣減等核心業務，對數據的精確性要求不允許任何錯誤。

樂觀鎖 (Optimistic Lock)

核心哲學

樂觀鎖的哲學是：「永遠假設最好的情況會發生」。它認為在併發環境下，數據衝突發生的機率很低，因此在讀取或修改數據時，不加任何顯式鎖定。它允許所有的事務自由地讀取和修改數據，只在最終提交更新時才檢查是否存在衝突。如果發現衝突，則通知應用程式進行重試或回滾。這就像你和同事都默默地在各自改文件，直到你想存檔時，才發現同事已經改好並存檔了，這時需要去處理衝突。

工作原理

樂觀鎖通常不是資料庫層面的鎖，而是需要應用程式層面來實現。最常見的實現方式是使用版本號 (Version Number) 或時間戳 (Timestamp) 欄位。

以版本號為例：

  1. 讀取時帶回版本號：
    • 當事務 A 讀取一條數據時，也會將該數據的版本號（例如 version 欄位）一併讀取到應用程式的記憶體中。
      SELECT id, name, version FROM products WHERE id = 123;
-- Result: (id: 123, name: "舊商品", version: 1)
  2. 修改數據：
    • 事務 A 在應用程式中修改了數據（例如將 name 改為 “新商品”），但此時不更新資料庫。
  3. 寫入時比對版本號：
    • 當事務 A 準備將修改後的數據寫回資料庫時，它會帶上之前讀取到的版本號 (version: 1)，並在 WHERE 條件中判斷資料庫中當前數據的版本號是否與之相等。
      UPDATE products SET name = "新商品", version = 2
WHERE id = 123 AND version = 1;
    • 如果更新成功 (影響行數為 1)：表示資料庫中該數據的版本號 (version: 1) 未被其他事務修改，這次更新是安全的，同時將版本號遞增 (version = 2)。
    • 如果更新失敗 (影響行數為 0)：表示在事務 A 讀取後到寫入期間，有其他事務已經修改並提交了該數據，導致資料庫中的 version 欄位不再是 1。此時發生了衝突。應用程式需要捕捉這個更新失敗，然後可以選擇：
      • 重試：重新讀取最新數據和版本號，讓用戶再次編輯或自動合併。
      • 報錯：提示用戶數據已更新，讓用戶選擇如何處理。

優點

  • 併發性高：在整個讀取和處理過程中，不鎖定數據庫資源，允許大量併發操作同時進行。
  • 無死鎖：自身不產生鎖定，因此不會有死鎖問題。
  • 適用於分佈式系統：由於基於版本號判斷，與資料庫的鎖機制解耦，更容易在多個服務或資料庫實例之間實現併發控制。

缺點

  • 衝突處理複雜：需要應用程式層面來處理更新失敗後的重試、合併或報錯邏輯，增加了程式碼的複雜度。
  • 性能回退：如果數據衝突發生的機率非常高，導致頻繁的重試，反而可能比悲觀鎖的性能更差。
  • 僅適用於更新：主要針對更新操作防止丟失更新，對於髒讀、不可重複讀則需要資料庫本身的事務隔離級別來保證。

適用場景

  • 低寫入衝突：預期數據衝突發生的機率不高。
  • 高讀取量：系統以讀取操作為主，寫入操作相對較少。
  • 長事務：需要較長時間處理的業務邏輯（例如用戶編輯一個複雜的表單），避免長時間持有鎖。
  • 網頁編輯器、商品資訊更新、用戶資料修改等。

悲觀鎖 vs. 樂觀鎖：核心區別一覽

特性 悲觀鎖 (Pessimistic Lock) 樂觀鎖 (Optimistic Lock)
哲學 預防式：假定會衝突，先鎖定。 事後檢測：假定不會衝突，提交時檢查。
衝突處理 立即阻塞其他操作。 允許操作發生，提交時檢測，衝突則失敗回滾或重試。
併發性 低：鎖定期間阻塞其他操作。 高：讀取和處理期間不阻塞。
死鎖 可能發生。 不會發生。
實現方式 資料庫鎖（FOR UPDATE），通常由資料庫管理系統維護。 應用程式層面實現（版本號、時間戳），透過 WHERE 條件判斷。
適用場景 高併發寫入、短事務、嚴格一致性要求。 高併發讀取、長事務、低寫入衝突、分佈式系統。

如何選擇合適的鎖策略？

選擇樂觀鎖還是悲觀鎖，沒有絕對的答案，需要根據具體的業務場景、數據特性和系統設計目標進行權衡：

  1. 考量衝突機率：
    • 如果數據寫入衝突非常頻繁，或者任何衝突都不可接受（如銀行轉帳），則悲觀鎖可能是更安全、更直接的選擇。
    • 如果數據寫入衝突較為罕見，且系統對併發性要求較高，樂觀鎖能提供更好的性能。
  2. 考量事務長度：
    • 如果事務非常短暫，悲觀鎖持有鎖的時間短，對整個系統影響小。
    • 如果事務持續時間長（例如用戶長時間編輯），悲觀鎖會嚴重降低併發性，此時樂觀鎖更優。
  3. 考量系統架構：
    • 在單體應用且單一資料庫的情況下，悲觀鎖實現相對簡單。
    • 在微服務、分佈式系統中，悲觀鎖的實現非常困難且不推薦，樂觀鎖是更自然的選擇。

結論

鎖機制是併發控制的核心，理解悲觀鎖與樂觀鎖的原理與適用場景，是專業開發者和架構師的必備技能。它們不是非此即彼的選擇，而是在不同的業務需求和性能目標之間進行深思熟慮的權衡。

無論是選擇了保守的悲觀鎖，還是採用了靈活的樂觀鎖，目的都是一致的：確保數據的生命線——在無數次的讀寫、修改與存取中，都能保持其真實、完整與可靠的面貌。
