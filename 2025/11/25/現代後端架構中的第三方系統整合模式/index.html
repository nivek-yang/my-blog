現代後端架構中的第三方系統整合模式

發表於 2025-11-25 分類於 技術筆記

身為軟體工程師，我們很少打造一個完全獨立運作的系統。從支付串接、雲端通訊、身份驗證，到各式各樣的 SaaS 服務，系統總是需要與外部世界溝通。

「整合」看似簡單，但不同的場景需要不同的策略。選擇錯誤的整合模式，輕則導致效能低落、資源浪費；重則可能造成資料遺失、系統崩潰。

本篇文章將深入五種主流的系統整合模式，並用流程圖解析它們的運作方式。

最直觀的互動 — Direct API Call (同步請求)

這是最基礎、最常見的模式。當系統需要第三方系統的資料或服務來完成某個任務時，就發起一個 API 請求，然後原地等待，直到對方回傳結果。

生活比喻：去咖啡店點餐，然後站在櫃檯前等待，直到店員把做好的咖啡交給你。

運作流程

sequenceDiagram
    participant User as 使用者
    participant SystemA as 你的系統
    participant SystemB as 第三方系統

    User->>SystemA: 發起請求 (例如：下訂單)
    SystemA->>SystemB: 發起 API 請求 (例如：驗證信用卡)
    note right of SystemA: 系統 A 處理程序被阻擋 (Blocked)，<br/>等待系統 B 回應。
    SystemB-->>SystemA: 回應 API 結果 (成功/失敗)
    SystemA-->>User: 回應最終結果

優缺點分析

  • 優點：
    • 實現簡單：邏輯直觀，就是一次函式呼叫。
    • 即時回饋：可以立即知道操作成功或失敗。
  • 缺點：
    • 緊密耦合 (Tightly Coupled)：系統 A 強烈依賴系統 B 的穩定性與效能。
    • 阻塞等待：如果系統 B 回應緩慢，系統 A 的執行緒會被長時間佔用，影響自身服務的吞吐量。
    • 超時風險：網路延遲或系統 B 處理時間過長，容易導致請求超時失敗。

適用場景

  • 需要立即性和原子性結果的操作。
  • 範例：信用卡授權、驗證使用者身份、查詢即時庫存。

勤勞的詢問者 — Polling (輪詢)

當要等待一個來自第三方系統的非同步任務完成時，最簡單粗暴的方法就是輪詢。系統會每隔一段時間就主動去問第三方系統：「嘿，那個任務完成了嗎？」

生活比喻：在微波爐前，每 10 秒鐘就打開一次門，看看食物熱好了沒有。

運作流程

sequenceDiagram
    participant SystemA as 你的系統
    participant SystemB as 第三方系統

    SystemA->>SystemB: 發起一個非同步任務 (例如：產生報表)
    SystemB-->>SystemA: 回應 (任務已開始，ID: 123)

    loop 每隔 X 秒/分鐘
        SystemA->>SystemB: 查詢任務狀態 (ID: 123)
        SystemB-->>SystemA: 回應 (處理中...)
    end

    SystemA->>SystemB: 查詢任務狀態 (ID: 123)
    SystemB-->>SystemA: 回應 (已完成，下載連結: ...)

優缺點分析

  • 優點：
    • 實現簡單：在客戶端（你的系統）側的邏輯很單純，就是一個定時任務。
    • 對第三方系統要求低：對方不需要支援任何特殊功能，只要提供一個狀態查詢的 API 即可。
  • 缺點：
    • 資源浪費：大量的查詢請求可能都是無效的（任務還在處理中），造成網路頻寬和伺服器資源的浪費。
    • 延遲性：無法即時得知任務完成。如果輪詢間隔是 1 分鐘，那麼最多會有 1 分鐘的延遲。
    • 擴展性差：當需要輪詢的任務數量增加時，對雙方系統的壓力都會劇增。

適用場景

  • 第三方系統不支援 Webhook。
  • 對任務完成的即時性要求不高。
  • 範例：等待一份大型報表產生、查詢 AI 模型訓練進度。

優雅的回調 — Webhook (事件驅動)

Webhook 徹底反轉了 Polling 的溝通模式，從「我來問你」變成了「你來通知我」。在發起任務時，會提供一個回調 URL (Callback URL)，告訴第三方系統：「任務完成後，請往這個地址發一個 HTTP POST 請求通知我。」

生活比喻：在餐廳候位，不用一直去問櫃檯，而是留下手機號碼，輪到你時餐廳會主動打電話來。

運作流程

sequenceDiagram
    participant SystemA as 你的系統
    participant SystemB as 第三方系統

    note over SystemA, SystemB: 階段一：註冊回調
    SystemA->>SystemB: 發起任務，並提供 Webhook URL
    SystemB-->>SystemA: 回應 (任務已收到)

    note over SystemA, SystemB: 階段二：任務完成後，非同步通知
    SystemB->>SystemA: 向註冊的 Webhook URL 發送 POST 請求 (攜帶結果資料)
    SystemA-->>SystemB: 回應 HTTP 200 OK (表示已收到通知)

優缺點分析

  • 優點：
    • 高效率：沒有多餘的查詢請求，只有在事件發生時才會通訊。
    • 近乎即時：事件完成後能立刻收到通知。
    • 伺服器友好：大大降低了雙方系統的負載。
  • 缺點：
    • 需要公網端點 (Endpoint)：系統必須提供一個能從公網訪問的 URL。
    • 可靠性問題：如果通知當下系統剛好故障或在部署，這次通知就可能遺失（除非對方有重試機制）。
    • 安全性考量：需要驗證收到的請求確實來自於第三方系統，而不是惡意偽造的（通常使用簽章驗證）。

適用場景

  • 主流的事件驅動整合方式。
  • 範例：支付成功通知、GitHub push 後觸發 CI/CD、收到新郵件或簡訊的通知。

永不斷線的對話 — Websockets

當需要與第三方系統進行持續性、雙向、即時的溝通時，以上模式可能都不夠用。Websockets 會建立一個長連線 (Persistent Connection)，允許雙方在任何時候互相發送訊息。

生活比喻：不是打電話和掛斷，而是一直保持通話的對講機。

運作流程

sequenceDiagram
    participant SystemA as 你的系統
    participant SystemB as 第三方系統

    SystemA->>SystemB: 發起 HTTP Request (請求升級為 Websocket)
    SystemB-->>SystemA: 回應 HTTP 101 (切換協議)
    note over SystemA, SystemB: Websocket 連線建立成功

    SystemB->>SystemA: 推送即時訊息 (例如：股價更新)
    SystemB->>SystemA: 推送另一條訊息
    SystemA->>SystemB: 發送指令 (例如：訂閱其他股票)

優缺點分析

  • 優點：
    • 極低延遲：真正的即時通訊，訊息傳遞非常快。
    • 雙向溝通：不像 Webhook 只能單向通知，Websockets 允許雙方隨時互傳資料。
    • 效能高：連線建立後，後續的訊息交換省去了 HTTP 的標頭開銷。
  • 缺點：
    • 狀態管理複雜：需要維護連線的生命週期（建立、心跳、斷線重連）。
    • 伺服器資源：維持大量長連線會消耗伺服器內存。
    • 支援度：並非所有第三方服務都提供 Websockets API。

適用場景

  • 需要高頻率、雙向的即時資料交換。
  • 範例：交易所的即時報價 API、線上多人協作工具、網頁聊天室。

終極解耦 — Message Queue (訊息佇列)

在複雜的分散式系統或微服務架構中，可以使用一個中介層——訊息佇列（如 RabbitMQ, Kafka）來徹底解耦系統。系統 A 只需將訊息（任務）發布到佇列中，就可以立即完成自己的工作。系統 B（或其他消費者）則在自己有空時去佇列中取出訊息進行處理。

生活比喻：把信件投進郵筒就離開了，郵差會在稍後的時間點來收信並完成投遞，整個過程無需等待。

運作流程

sequenceDiagram
    participant SystemA as 生產者 (Producer)
    participant Broker as 訊息佇列 (Message Queue)
    participant SystemB as 消費者 (Consumer)

    SystemA->>Broker: 發布訊息 (Publish Message)
    note right of SystemA: SystemA 的任務完成，<br/>無需關心誰來處理。

    Broker->>SystemB: 推送/拉取訊息
    SystemB->>SystemB: 處理訊息...
    SystemB->>Broker: 確認訊息已處理 (Acknowledge)

優缺點分析

  • 優點：
    • 極致解耦：生產者和消費者完全獨立，互不感知對方存在。
    • 高可靠性與韌性：即使消費者系統當機，訊息仍會安全地保存在佇列中，待其恢復後再處理。
    • 削峰填谷 (Load Balancing)：能有效應對瞬間的流量洪峰，保護後端服務不被衝垮。
    • 易於擴展：可以輕鬆地增加更多消費者來平行處理訊息，提高系統吞吐量。
  • 缺點：
    • 架構複雜度：需要引入並維護一個新的中介層（Broker）。
    • 非同步：不適用於需要即時回饋的場景。
    • 最終一致性：資料的處理是非同步的，需要接受短時間的資料不一致。

適用場景

  • 微服務之間的通訊。
  • 處理耗時的背景任務（影片轉檔、發送大量通知）。
  • 需要保證訊息 100% 不遺失的關鍵業務流程。

整合模式比較

整合模式 耦合度 即時性 效率 實現複雜度 核心場景
Direct API Call 高 最高 中 (受對方影響) 低 同步、原子性操作
Polling 中 差 低 低 兜底方案，對方無 Webhook
Webhook 低 高 高 中 非同步事件通知
Websockets 中 最高 高 高 持續性雙向通訊
Message Queue 極低 差 (非同步) 極高 高 系統解耦、流量削峰

結論

沒有最好的整合模式，只有最適合你的業務場景的模式。在設計系統時，問自己幾個問題：

  • 需要即時的結果嗎？還是可以非同步處理？
  • 第三方系統支援哪些整合方式？
  • 對系統的可靠性、擴展性要求有多高？
  • 願意為了更高的韌性而增加架構的複雜度嗎？

理解這些模式的本質與權衡，將使你在架構設計的路上走得更遠、更穩。
