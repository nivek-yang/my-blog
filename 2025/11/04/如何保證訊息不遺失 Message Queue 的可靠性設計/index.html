如何保證訊息不遺失？深入剖析 Message Queue 的可靠性設計

發表於 2025-11-04 分類於 技術筆記

在現代微服務與分散式系統架構中，訊息佇列（Message Queue, MQ）扮演著不可或缺的角色。它作為系統間的非同步通訊中樞，有效地實現了服務解耦、流量削峰、以及最終一致性。然而，一個關鍵問題始終縈繞在架構師和開發者的心頭：「如何才能 100% 保證訊息不會遺失？」

事實上，「100% 不遺失」是一個極限目標，但在實務中，可以透過一系列精密的設計，將訊息遺失的風險降至無限趨近於零。

本篇文章文將深入訊息傳遞的完整生命週期，剖析每個環節可能出現的風險，並探討 MQ 系統是如何透過各種機制來確保訊息的高可靠性。

訊息傳遞的三個關鍵階段

一則訊息從誕生到消亡，主要會經歷三個階段：

  1. 生產階段：從生產者（Producer）創建訊息，到成功將其發送到 MQ Broker。
  2. 儲存階段：訊息在 MQ Broker 中被安全地儲存，等待消費者來擷取。
  3. 消費階段：從 MQ Broker 將訊息推送（或被拉取）給消費者（Consumer），直到消費者成功處理完畢。

任何一個環節出現問題，都可能導致訊息遺失。因此，可靠性設計必須針對這三個階段分別進行。

1. 生產階段：確保訊息成功抵達 Broker

風險點：生產者發送訊息後，可能因為網路抖動、Broker 瞬間故障等原因，導致訊息並未真正送達 Broker。生產者若對此不知情，便會造成訊息的遺失。

解決方案：異步確認機制 (Confirmation)

絕大多數主流的 MQ 都提供了發送方確認機制。其核心思想是，Broker 在收到訊息並完成相應處理（如寫入磁碟）後，會回傳一個確認（ACK）或不確認（NACK）的回應給生產者。

  • ACK (Acknowledge)：表示訊息已成功接收。
  • NACK (Negative Acknowledge)：表示訊息因某種原因（如佇列已滿）被拒絕。

實作策略：

  1. 開啟 Confirm 模式：在生產者端設定，要求 Broker 對每條訊息進行確認。
  2. 處理回呼：生產者需要實作監聽回呼函式。當收到 ACK 時，表示發送成功；當收到 NACK 或在一定時間內未收到任何回應（Timeout），則表示發送失敗。
  3. 失敗重試：對於發送失敗的訊息，生產者必須要有重試機制。可以將失敗的訊息暫存於記憶體、資料庫或日誌檔案中，然後定時重新發送，直到收到 Broker 的 ACK 為止。

注意：重試機制可能會導致訊息重複發送。這就引出了一個極其重要的概念——生產端冪等性，將在文末統一探討。

2. 儲存階段：確保 Broker 不會弄丟訊息

風險點：訊息雖然成功抵達 Broker，但如果只存在於記憶體中，一旦 Broker 程式當機或伺服器斷電，所有訊息將會灰飛煙滅。

解決方案：持久化 (Persistence) + 叢集同步 (Clustering/Replication)

a. 持久化 (Persistence)

這是最基本的可靠性保障。當 Broker 收到訊息後，不是只放在記憶體，而是將其寫入磁碟。這樣即使 Broker 崩潰重啟，也能從磁碟中恢復訊息資料，不會遺失。

  • RabbitMQ：需要將佇列（Queue）和訊息（Message）都設定為 durable。
  • Kafka：其設計天生就是基於磁碟日誌檔案（Log），所有訊息都會被追加到磁碟上的 Partition 檔案中，因此本身就具備高度的持久化能力。

權衡：持久化會帶來 I/O 開銷，犧牲一定的效能來換取高可靠性。

b. 叢集同步 (Clustering/Replication)

單點的磁碟持久化只能防止單機故障，但如果整台伺服器或磁碟損壞，訊息依然會遺失。為了解決單點故障（Single Point of Failure），需要將 Broker 組成叢集，並啟用資料同步機制。

  • Kafka：採用 Leader-Follower 的副本（Replica）機制。生產者只向 Leader 分區寫入訊息，Follower 分區會自動從 Leader 同步資料。只有當訊息被同步到指定數量（min.insync.replicas）的副本後，Broker 才會向生產者發送 ACK。這確保了即使 Leader 節點掛掉，訊息依然在其他 Follower 節點上有備份。
  • RabbitMQ：提供 Mirrored Queues（鏡像佇列）功能，可以將一個佇列的訊息完整地複製到叢集中的多個節點上。

3. 消費階段：確保訊息被成功處理

風險點：這是最容易被忽視，也是最常出問題的地方。Broker 將訊息發送給消費者後，如果消費者在處理訊息的過程中（例如，寫入資料庫）突然崩潰，而 Broker 卻以為訊息已經被成功消費並將其刪除，這條訊息就永遠遺失了。

解決方案：手動 ACK 機制 (Manual Acknowledgement)

為了避免這種情況，MQ 提供了消費者確認機制。

  • 自動 ACK (Auto ACK)：Broker 發出訊息後，立即將其標記為已消費。這種模式非常高效，但極其不安全，生產環境應避免使用。
  • 手動 ACK (Manual ACK)：Broker 發出訊息後，會將該訊息標記為「投遞中」（unacked），並等待消費者的明確回覆。
    • 消費者必須在業務邏輯完全處理成功後，才向 Broker 發送 ACK 指令。Broker 收到 ACK 後，才會將訊息徹底刪除。
    • 如果消費者在處理過程中崩潰，或者明確發送了 NACK（或Reject），Broker 將會在一段時間後將這條訊息重新投遞給另一個（或同一個）消費者。

正確的消費流程：

// 偽代碼
function processMessage(message) {
    try {
        // 1. 執行核心業務邏輯，例如寫入資料庫
        saveToDatabase(message.data);

        // 2. 業務成功後，才手動發送 ACK
        channel.ack(message);

    } catch (error) {
        // 3. 業務處理失敗
        // 可以選擇 NACK 並讓訊息重回佇列 (requeue=true)
        // 或將訊息發送到一個專門的「死信佇列」(Dead-Letter Queue) 以便後續分析
        channel.nack(message, { requeue: false });
        logError(error);
    }
}

關鍵的附帶問題：冪等性 (Idempotency)

無論是生產端的重試，還是消費端的重queue，都會導致同一條訊息被多次處理的可能。如果業務邏輯不具備冪等性，就會產生嚴重的副作用（例如，重複下單、重複扣款）。

冪等性：指對同一個操作執行一次或多次，其產生的影響和結果都是相同的。

如何保證冪等性？

  • 唯一 ID + 判重表：為每條訊息生成一個全域唯一的業務 ID。在消費端建立一張紀錄表，處理訊息前先查詢該 ID 是否已被處理過。
  • 資料庫唯一約束：利用資料庫的 UNIQUE KEY 約束，當重複插入具有相同唯一鍵的資料時，操作會失敗，從而避免重複處理。
  • 樂觀鎖：使用版本號（version）機制，更新資料前檢查版本號是否匹配，避免併發場景下的重複更新。

總結

要保證訊息不遺失，需要從生產、儲存到消費的全鏈路進行系統性設計：

階段 可靠性機制 關鍵配置/實作
生產階段 發送方確認 (Confirm) - 開啟 Confirm 模式
- 實作 ACK/NACK 回呼
- 建立失敗重試機制
儲存階段 持久化 (Persistence) - Queue 和 Message 設為 durable (RabbitMQ)
- Topic 資料本身就是持久化的 (Kafka)
叢集與副本 (Replication) - 配置主從副本 (Kafka)
- 使用鏡像佇列 (RabbitMQ)
消費階段 手動 ACK (Manual Ack) - 關閉 Auto ACK
- 業務處理成功後再手動 ACK
- 處理失敗時轉入死信佇列
全鏈路 冪等性保障 (Idempotency) - 為訊息建立唯一業務 ID
- 消費端進行重複處理判斷

訊息傳遞的可靠性並非單一技術，而是一套組合拳。透過對每個環節的精雕細琢，才能構建出一個真正健壯、值得信賴的分散式系統。
