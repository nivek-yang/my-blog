告別批次處理：Change Data Capture (CDC) 的異步革命

發表於 2025-11-13 分類於 技術筆記

在數據驅動的時代，對數據的「即時性」要求越來越高。然而，許多系統的數據同步仍然依賴著一種古老而笨拙的方式——批次處理 (Batch Processing)。

想像一下這個場景：

  • 一個 ETL (Extract-Transform-Load) 任務在每天午夜執行，將線上交易資料庫 (OLTP) 的數據同步到數據倉庫 (Data Warehouse)。這意味著業務分析師看到的報表，永遠是昨天的數據。
  • 為了更新搜尋引擎中的商品資訊，需要寫一個定時任務，每 10 分鐘輪詢一次商品資料表，找出 updated_at 在最近 10 分鐘內的記錄。這種輪詢不僅給資料庫帶來了不必要的壓力，還可能遺漏「刪除」操作。

這些方法的共同問題是：延遲、資源浪費和數據不一致。

有沒有一種更優雅、更即時的方式？答案就是 Change Data Capture (CDC)。

什麼是 CDC (Change Data Capture)？

CDC 是一種軟體設計模式，用於識別和捕獲資料庫中的數據變更（INSERT, UPDATE, DELETE），並將這些變更事件以串流 (Stream) 的形式，即時地傳遞給下游的消費者。

一個絕佳的類比：

  • 傳統輪詢：就像每小時打電話給圖書館，詢問「有沒有新書到？」，圖書館員需要放下手邊工作，幫你查一遍。這既打擾了圖書館員，也無法第一時間知道新書上架的消息。
  • CDC：就像向圖書館「訂閱」了新書通知服務。一旦有新書上架，圖書館會立刻發一條簡訊給你。無需再主動詢問，總能即時獲取資訊，而且圖書館員的壓力也大大降低。

CDC 的核心思想是，將資料庫視為一個產生「事實」的地方，而每一次數據變更，都是一個不可變的「事件」。我們的工作，就是去監聽並響應這些事件。

CDC 是如何運作的？深入核心原理

CDC 的實現方式有多種，但它們的優劣和對源資料庫的影響差異巨大。

1. 基於查詢 (Query-Based) - 最不推薦

這是最原始的方式，通常依賴於一個 last_updated_at 之類的時間戳欄位。

  • 工作方式：定時執行 SELECT * FROM table WHERE updated_at > ? 查詢。
  • 缺點：
    • 無法捕獲 DELETE：一行記錄被刪除後，就再也查不到它了。
    • 高延遲：數據同步的即時性取決於輪詢頻率。
    • 性能開銷：頻繁的全表或索引掃描會給源資料庫帶來巨大壓力。

2. 基於觸發器 (Trigger-Based)

在資料庫層面，為要監控的表建立 INSERT, UPDATE, DELETE 觸發器。

  • 工作方式：當主表發生變更時，觸發器會將變更的內容（舊數據、新數據）寫入一個獨立的「日誌表」或「事件表」。CDC 工具再從這張表中讀取數據。
  • 缺點：
    • 侵入性強：需要在源資料庫中建立額外的資料庫物件。
    • 性能影響：觸發器在原始的資料庫交易中同步執行，會增加主業務的響應延遲。

3. 基於交易日誌 (Log-Based) - 現代 CDC 的黃金標準

這是目前最流行、最高效的方式。它利用了資料庫自身的交易日誌 (Transaction Log)。

幾乎所有主流資料庫（如 MySQL 的 binlog、PostgreSQL 的 WAL、Oracle 的 Redo Log）都有一個交易日誌。這個日誌的原始目的是為了數據庫的備份、還原和主從複製。它以極高的效率，忠實地記錄了資料庫中發生的每一次數據變更。

  • 工作方式：CDC 工具偽裝成一個從庫 (Slave/Replica)，去讀取並解析資料庫的交易日誌。它將日誌中的底層變更事件（如 “在 users 表的 offset 123 處，將欄位 ‘status’ 的值從 ‘active’ 改為 ‘inactive’”）轉換為更易於理解的數據事件流。
  • 優點：
    • 低延遲、高吞吐：直接讀取日誌，繞過了 SQL 查詢層，接近即時。
    • 對源資料庫性能影響極小：讀取日誌是一個非同步的、輕量級的操作。
    • 數據完整性高：可以捕獲包括 DELETE 在內的所有操作，甚至 DDL（如 ALTER TABLE）變更。
    • 非侵入性：無需修改源資料庫的 Schema。

主流 CDC 架構與生態系

現代基於日誌的 CDC 架構，通常以 Debezium + Kafka 為核心。

  • Debezium：一個開源的分散式 CDC 平台，是這個領域的事實標準。它為主流資料庫（MySQL, PostgreSQL, MongoDB 等）提供了源連接器 (Source Connector)。
  • Kafka Connect：一個用於在 Apache Kafka 和其他系統之間可靠地串流數據的框架。Debezium 的連接器就運行在 Kafka Connect 之上。
  • Apache Kafka：一個高吞吐、可擴展的分散式消息佇列，是 CDC 事件流的完美載體和緩衝區。

為什麼應該在專案中使用 CDC？核心應用場景

CDC 不僅僅是一項技術，它是一種能解鎖眾多架構可能性的「催化劑」。

  1. 微服務間的數據同步
    在微服務架構中，每個服務都擁有自己的資料庫。當服務 A 需要服務 B 的數據時，傳統做法是透過 API 呼叫。但如果服務 A 需要對 B 的數據進行複雜查詢或聚合，API 模式就會變得低效。透過 CDC，服務 B 可以將其數據變更發佈到 Kafka，服務 A 可以訂閱這些變更，在自己的資料庫中維護一份「物化視圖」，從而實現高效的本地查詢。

  2. 即時數據倉儲與分析
    告別 T+1 的數據延遲。透過 CDC，交易數據可以即時地流入數據倉庫或數據湖，讓業務分析師能夠基於最新的數據進行決策。

  3. 快取同步與失效 (Cache Invalidation)
    當資料庫中的數據更新後，如何保證 Redis 等快取中的數據也能同步更新？CDC 提供了完美的解決方案。監聽資料庫的變更事件，一旦有更新或刪除，就發送一個命令去清除或更新 Redis 中的對應快取。

  4. 搜尋引擎同步
    保持 Elasticsearch 或 OpenSearch 中的索引與主資料庫同步，是 CDC 的一個經典應用。任何商品的增、刪、改，都能即時反映到搜尋引擎中，確保用戶搜到的永遠是最新資訊。

T+1 的數據延遲，意思是：今天（T日）產生的數據，要到明天（T+1日）才能被查詢、分析或使用。

挑戰與考量

CDC 雖然強大，但也並非萬能藥。在實施前需要考慮：

  • 初始快照 (Initial Snapshot)：在開始監聽增量變更之前，如何獲取數據庫的全量基準數據？Debezium 等工具提供了對此的內建支援。
  • Schema 演進：當源資料庫的表結構發生變化時（如增加欄位），CDC 管道需要能夠優雅地處理這些 DDL 變更。
  • 事件傳遞保證：需要理解 Kafka 等消息系統提供的「至少一次 (at-least-once)」或「精確一次 (exactly-once)」傳遞語義，以應對可能的重複事件。

At-Most-Once (最多一次):消息最多只會被傳遞一次。可能會丟失，但絕不會重複。

At-Least-Once (至少一次):消息保證會被傳遞，絕不會丟失，但可能會重複。

Exactly-Once (精確一次):消息不多不少，精確地被傳遞一次。既不丟失，也不重複。

結論

CDC 代表了一種從「請求-響應」的批次思維，到「事件驅動」的串流思維的轉變。它將資料庫從一個被動的數據孤島，轉變為一個主動的、即時的事件源泉。

透過解耦數據的生產者和消費者，CDC 為構建高彈性、可擴展、即時響應的現代數據架構鋪平了道路。如果還在為數據同步的延遲和複雜性而煩惱，那麼，是時候深入了解 Change Data Capture 了。
