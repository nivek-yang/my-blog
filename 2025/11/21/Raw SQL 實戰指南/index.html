當 ORM 不夠用時：一份 Raw SQL 實戰指南

發表於 2025-11-21 分類於 技術筆記

身為 軟體開發者，我們都熱愛 ORM。它優雅、直觀，將複雜的 SQL 操作抽象化為簡潔的程式碼，讓我們能專注於業務邏輯。但在開發過程中，總會遇到一些時刻，發現碰到了 ORM 的天花板。

有些任務，無論是為了極致的效能、絕對的資料完整性，還是為了利用特定資料庫的獨門絕技，都無法單純依靠 ORM 來完成。

本篇文章將以 Python Django 框架為實戰案例，探討如何使用 Django Migrations 中的 migrations.RunSQL 來釋放資料庫的潛能。從關鍵的安全性實戰案例: 行級安全性 (Row-Level Security, RLS) 開始，探索一系列 ORM 無法觸及，但對專業應用至關重要的強大功能。

用 Django Migration 優雅地管理 RLS

想像一下，有一個多銷售員的應用，每個銷售員都應該只能看到自己的銷售紀錄。通常會在每個查詢後面加上 .filter(salesperson=request.user)。但如果忘了呢？

這就是 PostgreSQL 的資料列層級安全性 (Row-Level Security, RLS) 大顯身手的地方。它是一道資料庫層級的安全網，確保即使應用程式程式碼有疏漏，資料庫本身也會強制執行存取規則。而管理這些規則最專業的方式，就是透過 Migrations。

場景：銷售模型

# sales_app/models.py
from django.db import models
from django.contrib.auth.models import User

class Sale(models.Model):
    product = models.CharField(max_length=100)
    amount = models.DecimalField(max_digits=10, decimal_places=2)
    salesperson = models.ForeignKey(User, on_delete=models.CASCADE)

步驟 1：建立一個空的 Migration 檔案

因為不修改模型結構，所以需要手動建立一個空的遷移檔案來存放 SQL。

python manage.py makemigrations sales_app --empty --name add_rls_to_sales

步驟 2：使用 migrations.RunSQL

打開新建立的遷移檔案 (sales_app/migrations/0002_...py)，用以下內容替換它。RunSQL 允許定義「正向」(套用規則) 和「反向」(撤銷規則) 的 SQL，這對於版本控制至關重要。

# sales_app/migrations/0002_add_rls_to_sales.py
from django.db import migrations

TABLE_NAME = "sales_app_sale"

APPLY_RLS_SQL = f"""
-- 1. 在資料表上啟用 RLS 總開關
ALTER TABLE {TABLE_NAME} ENABLE ROW LEVEL SECURITY;

-- 2. 建立核心策略
CREATE POLICY select_own_sales_policy ON {TABLE_NAME}
FOR SELECT
USING (salesperson_id = (
    SELECT id FROM auth_user WHERE username = current_user
));

-- 3. (建議) 強制連資料表擁有者也遵守 RLS
ALTER TABLE {TABLE_NAME} FORCE ROW LEVEL SECURITY;
"""

REMOVE_RLS_SQL = f"""
DROP POLICY IF EXISTS select_own_sales_policy ON {TABLE_NAME};
ALTER TABLE {TABLE_NAME} DISABLE ROW LEVEL SECURITY;
"""

class Migration(migrations.Migration):
    dependencies = [
        ('sales_app', '0001_initial'),
    ]
    operations = [
        migrations.RunSQL(
            sql=APPLY_RLS_SQL,
            reverse_sql=REMOVE_RLS_SQL,
        )
    ]

關鍵解析：USING 子句中的子查詢是連接 Django 和 PostgreSQL 的橋樑。current_user 是 PostgreSQL 中代表當前資料庫連線角色的變數。這個子查詢找到了與當前連線角色同名的 Django 使用者的 id，並用它來過濾銷售紀錄。

步驟 3：套用 Migration

python manage.py migrate

資料庫現在有了一道安全防線。任何繞過應用程式邏輯的查詢，都將被 RLS 策略攔截。

Raw SQL 的其他應用

RLS 只是冰山一角。一旦掌握了 migrations.RunSQL，一整個新世界的大門就此打開。以下是幾個 ORM 鞭長莫及，但 Raw SQL 極其有用的場景：

1. 查詢計畫分析 (EXPLAIN)

說明 EXPLAIN 是資料庫的自我剖析工具，描述它將如何執行一個查詢。這是資料庫效能調校的第一神器。

ORM 為何做不到？ ORM 的工作是產生 SQL，而 EXPLAIN 的工作是分析 SQL。

實戰技巧：可以輕鬆地在 Django 中分析任何 QuerySet 的效能。

from django.db import connection

# 建立一個想分析的 QuerySet
slow_queryset = Sale.objects.filter(amount__gt=1000).select_related('salesperson')

# 取得它將產生的 SQL
sql_query, params = slow_queryset.query.sql_with_params()

# 加上 EXPLAIN ANALYZE
explain_sql = f"EXPLAIN (ANALYZE, BUFFERS) {sql_query}"

# 執行並印出查詢計畫
with connection.cursor() as cursor:
    cursor.execute(explain_sql, params)
    query_plan = "\n".join(row[0] for row in cursor.fetchall())
    print(query_plan)

2. 資料庫視圖 (Database Views)

說明 一個由 SELECT 查詢定義的「虛擬資料表」，用來簡化複雜的 JOIN 查詢，讓我們把多張表的關聯資料當作一張單一的表來查詢。

ORM 為何做不到？ ORM 的核心是將 Python class 對應到實際儲存資料的資料表。它沒有內建語法來定義一個基於查詢的虛擬結構。

實戰技巧：在 migration 中建立 View，然後在 Django 中為它建立一個 managed = False 的模型。這樣能兩全其美：在資料庫層級擁有高效能的 View，在 Django 層級又能用優雅的 ORM 語法來操作它。

好的，完全理解！只展示 SQL 字串確實不夠完整，一個好的範例需要包含完整的 Migration 程式碼。

2. 資料庫視圖 (Database Views)

這是什麼？ 一個由 SELECT 查詢定義的「虛擬資料表」，用來簡化複雜的 JOIN 查詢，讓你把多張表的關聯資料當作一張單一的表來查詢。

ORM 為何做不到？ ORM 的核心是將 Python class 對應到實際儲存資料的資料表。它沒有內建語法來定義一個基於查詢的虛擬結構。

實戰技巧：在 migration 中建立 View，然後在 Django 中為它建立一個 managed = False 的模型。這樣你就兩全其美：在資料庫層級擁有高效能的 View，在 Django 層級又能用優雅的 ORM 語法來操作它。

步驟 1: 建立空的 Migration

python manage.py makemigrations sales_app --empty --name create_sales_report_view

步驟 2: 撰寫 Migration 檔案

編寫完整的 migration 檔案，包含正向和反向的 SQL。

# sales_app/migrations/0003_create_sales_report_view.py
from django.db import migrations

CREATE_VIEW_SQL = """
CREATE OR REPLACE VIEW sales_report_view AS
SELECT
    s.id,
    s.product,
    s.amount,
    u.username as salesperson_name
FROM
    sales_app_sale s
JOIN
    auth_user u ON s.salesperson_id = u.id;
"""

DROP_VIEW_SQL = "DROP VIEW IF EXISTS sales_report_view;"

class Migration(migrations.Migration):
    dependencies = [
        ('sales_app', '0002_add_rls_to_sales'), # 依賴於 sales_app_sale 表已存在
    ]
    operations = [
        migrations.RunSQL(
            sql=CREATE_VIEW_SQL,
            reverse_sql=DROP_VIEW_SQL,
        )
    ]

步驟 3: 建立對應的 Django 模型

接著，在 models.py 中建立一個模型來「對應」這個 View。

# sales_app/models.py

class SalesReportView(models.Model):
    # 欄位必須和 View 中的 SELECT 欄位完全對應
    product = models.CharField(max_length=100)
    amount = models.DecimalField(max_digits=10, decimal_places=2)
    salesperson_name = models.CharField(max_length=150)

    class Meta:
        managed = False  # 關鍵！告訴 Django 不要管理這張表的建立、修改、刪除
        db_table = 'sales_report_view'
        verbose_name = 'Sales Report'

注意：因為 View 沒有單一的主鍵，在模型中省略了 Django 自動產生的 id 欄位。Django 在查詢時會自動處理。如果 View 中有明確且唯一的欄位可以當作主鍵，可以加上 primary_key=True。

步驟 4: 套用 Migration 並使用

python manage.py migrate

現在，可以像查詢任何普通模型一樣，用優雅的 ORM 語法來查詢這個複雜的報表了！

# 在 views.py 或 shell 中
from .models import SalesReportView

# 獲取所有報表資料
reports = SalesReportView.objects.all()

# 進行過濾
high_value_reports = SalesReportView.objects.filter(amount__gt=5000)

for report in high_value_reports:
    print(f"Product: {report.product}, Sold by: {report.salesperson_name}, Amount: {report.amount}")

這個範例完美地展示了如何結合 Raw SQL 的強大能力和 Django ORM 的便利性。

3. 觸發器 (Triggers)

說明 當資料表發生 INSERT, UPDATE, DELETE 時自動執行的程序，常用於建立稽核日誌 (Audit Logs) 或維護複雜的資料一致性。

ORM 為何做不到？ 這是資料庫層級的自動化邏輯，比 Django Signals 更底層、更可靠。

實戰技巧：在 migration 中建立一個函式和一個觸發器，自動記錄價格變動。

-- migrations/000X_add_audit_trigger.py
CREATE_TRIGGER_SQL = """
CREATE OR REPLACE FUNCTION log_price_changes()
RETURNS TRIGGER AS $$
BEGIN
    IF (NEW.price <> OLD.price) THEN
        INSERT INTO price_history(product_id, old_price, new_price, changed_at)
        VALUES(OLD.id, OLD.price, NEW.price, now());
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER price_changes_trigger
AFTER UPDATE ON products_app_product
FOR EACH ROW EXECUTE FUNCTION log_price_changes();
"""

4. 進階全文檢索設定

說明 Django 內建的全文檢索很棒，但要支援中文分詞 (如 jieba) 或自訂同義詞，就需要直接設定資料庫的文字搜尋組態。

ORM 為何做不到？ ORM 沒有提供 CREATE TEXT SEARCH CONFIGURATION 這種底層的 DDL 指令。

實戰技巧：在 migration 中建立一個為中文優化的搜尋組態。

-- migrations/000X_create_chinese_fts.py (假設已安裝 pg_jieba)
CREATE_FTS_CONFIG_SQL = """
CREATE TEXT SEARCH CONFIGURATION chinese_jieba (PARSER = pg_catalog.default);
ALTER TEXT SEARCH CONFIGURATION chinese_jieba
    ALTER MAPPING FOR n,v,a,i,e,l,j
    WITH jieba, simple;
"""
# ... 在 RunSQL 中執行 ...

5. 管理資料庫擴充套件 (Extensions)

說明 啟用 PostgreSQL 強大的擴充套件，如 PostGIS (地理資訊)、pg_trgm (模糊字串比對) 等。

ORM 為何做不到？ CREATE EXTENSION 是資料庫管理指令。

實戰技巧：Django 為一些常用擴充套件提供了專門的 Migration 操作，這比手寫 RunSQL 更佳。

# migrations/000X_enable_pg_trgm.py
from django.contrib.postgres.operations import TrigramExtension

class Migration(migrations.Migration):
    operations = [
        TrigramExtension(),
    ]

指導原則

該如何決定何時使用 ORM，何時使用 Raw SQL 呢？有一個簡單的原則：

ORM 是應用程式與資料模型之間的橋樑，專注於資料的 CRUD 和關聯。而任何涉及到「資料庫本身的管理、效能內省、行為設定、功能擴充」的操作，都超出了它的職責範圍，需要下降到 SQL 層次來處理。

結論

透過熟練運用 migrations.RunSQL 和原生 SQL，不僅能解決 ORM 無法處理的難題，更能將我們的應用程式提升到一個新的高度——更安全、更高性能、功能更強大。
